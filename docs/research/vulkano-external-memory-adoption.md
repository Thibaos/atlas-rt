# vulkano adoption and external-memory surface for the Godot transport — feasibility research

## Executive answer

vulkano at the pinned rev (git master `70e3169`, `version = "0.35.0"` in its Cargo.toml, [Cargo.lock L1612-1615](https://github.com/vulkano-rs/vulkano)) already supports the vulkano side of both Windows transport candidates, with exactly one API-level gap: `DeviceMemory` exports file descriptors only — there is no `export_win32_handle`, and none on upstream master either (checked at eb3beec4, 2026-05-16; zero open issues or PRs mention external memory). The gap is closable with a one-call raw shim, not a fork: the generated `DeviceFunctions` group `khr_external_memory_win32: ash::khr::external_memory_win32::DeviceFn` is loaded on every `Device` (autogen-out/fns.rs L236, L388) and ash's struct carries `get_memory_win32_handle_khr`, so extension code can export a vulkano-owned `vk::DeviceMemory` through `Device::fns()` + `VulkanObject::handle()`. This finding upgrades godot-renderer-integration.md finding 8's flagged-unverified "allocation-level import" to verified-present: `DeviceMemory::import`/`try_import` exist with `MemoryImportInfo::Fd` and `::Win32` (plus D3D11 texture-handle imports).

Per sub-question of ticket 01:

- **(a) Adoption: fully supported.** `Instance::from_handle`/`from_handle_borrowed` (instance/mod.rs L520-543), `PhysicalDevice::from_handle` (device/physical.rs L95-98) — Godot's `VkPhysicalDevice` can be adopted directly, resolving the "match by handle" flagged inference from the earlier doc — and `Device::from_handle`/`from_handle_borrowed` (device/mod.rs L483-508). Adoption performs zero validation: the only requirement is the safety contract that the supplied create-infos mirror Godot's actual create-info (instance/mod.rs L516-518; device/mod.rs L479-481 says explicitly that only the `queue_family_index` parameters of `queue_create_infos` are used).
- **(b) Owning queue index >= 1 of a Godot-created family: supported through `Queue::from_handle`** (device/queue.rs L91-96), with an explicit shared-queue design (`QueueMutex` trait L191-214); `queue_index` is stored but "vulkano doesn't use it itself" (L84-87). The object model requires only: list the family in `DeviceCreateInfo.queue_create_infos` (command-pool creation validates against `active_queue_family_indices`, command_buffer/pool.rs L518-528), fetch the raw `vk::Queue` yourself (`Queue::new` is module-private, L38), and supply `DefaultQueueMutex` since a spare queue is untouched by Godot. The hard blocker remains engine-side: stock Godot creates exactly one queue per family (godot-renderer-integration.md finding 8), so index >= 1 does not exist until a VulkanHooks device create-info or an upstream change claims it.
- **(c) External memory and sync: import complete, export FD-only + shim, sync complete.** Memory import covers FD, Win32 (`OpaqueWin32`/`OpaqueWin32Kmt`) and D3D11 texture handles; export has `export_fd` (`OpaqueFd`/`DmaBuf`) and no Win32 wrapper. `Semaphore` and `Fence` have complete import AND export for FD and Win32 (plus Zircon for semaphores), so GPU-side cross-device synchronization is unblocked on the vulkano side; it stays blocked on Godot's side, which enables none of the sync extensions (godot-renderer-integration.md finding 7).
- **(d) Image for `texture_create_from_extension`: supported.** `ImageCreateInfo` exposes format/extent/samples/tiling/usage/initial_layout directly (image/sys.rs L1774-1793); `external_memory_handle_types` feeds `VkExternalMemoryImageCreateInfo` (L3208); `RawImage::bind_memory` validates imported/exported memory against the image's handle types (L900-936). The one vulkano-side constraint for externally-shared images: `initial_layout` must be `Undefined` (L1755-1756, validated L2944-2947). Layout after creation is fully caller-controlled — vulkano's `RawImage` imposes no transitions; the higher-level `Image` tracks layout state (image/mod.rs L113-115) and would drift from Godot's writes, so the RD-shared image should live at `RawImage` level with explicit transitions.

Consequence for ticket 04: on Windows, the cross-device candidate needs exactly one vulkano-side workaround (the Win32 export shim) plus the engine-side extension enablement from ticket 02; the same-device candidate needs no vulkano-side work at all but no spare queue on stock Godot either.

## Findings

1. **Adoption APIs exist for all three object levels and perform no validation — the create-infos you pass are declarations, not checks.** `Instance::from_handle(library, handle, create_info)` and `from_handle_borrowed` (vulkano@70e3169 vulkano/src/instance/mod.rs L520-526, L537-543) load all function pointers through `library.get_instance_proc_addr` (L578-581) and store `flags`/`api_version`/`enabled_extensions` verbatim from the supplied `InstanceCreateInfo` (L551-597); `from_handle_inner` never calls vkCreateInstance-adjacent validation. `Device::from_handle(physical_device, handle, create_info)` (vulkano/src/device/mod.rs L483-489, L502-508) stores `enabled_extensions`/`enabled_features` verbatim and derives only `active_queue_family_indices` from `queue_create_infos` (L533-541); its safety contract states "The `queue_create_infos` don't have to match exactly: only the `queue_family_index` parameters are used" (L479-481). `PhysicalDevice::from_handle(instance, handle)` (vulkano/src/device/physical.rs L95-98) is public and queries properties/extensions/queue-families on the adopted handle (L99-134). Practical requirements, all caller-side: (i) the `VulkanLibrary` must be the system loader — `VulkanLibrary::new()` loads `vulkan-1.dll` on Windows (vulkano/src/library.rs L62), the same library volk loads for Godot; (ii) `InstanceCreateInfo.enabled_extensions` must declare what Godot actually enabled, since vulkano consults it (e.g. the khr_get_physical_device_properties2 branch, physical.rs L114-118); (iii) `DeviceCreateInfo.enabled_extensions` must declare the hook-enabled device extensions, because vulkano's validated external-memory paths gate on `device.enabled_extensions()` (device/mod.rs L1466, L1574; device_memory.rs L1471, L1517) and declaring an unenabled extension makes the corresponding raw call a null-pointer dispatch.

2. **Queue ownership at index >= 1: vulkano's model is built for this, but it hands you no retrieval — you fetch the handle and adopt it.** `Queue::new` (the vkGetDeviceQueue2 wrapper) is `pub(super)` (vulkano/src/device/queue.rs L38), so on an adopted device the extension fetches the raw handle itself — via `Device::fns().v1_1.get_device_queue2` (the same call queue.rs L47 makes) or ash — and then adopts it: `Queue::from_handle(device, handle, queue_info, lock)` (L91-96) takes a `DeviceQueueInfo { flags, queue_family_index, queue_index }` (L261-278) plus `lock: Arc<dyn QueueMutex>`. The safety contract is explicit about the shared-queue case: "If you aren't given the `queue_index`, it's fine to make it up, as vulkano doesn't use it itself" (L84-87) and "The external code you share the queue with must use the same queue lock as vulkano. The `lock` parameter must be used to ensure this" (L88-89). `QueueMutex` (L191-214) exists to back the lock with the external library's locking; `DefaultQueueMutex` "should not be used when external code is sharing a queue with vulkano" (L222-228). Downstream checks that constrain the declarations: command pools require their family to be in `active_queue_family_indices` (vulkano/src/command_buffer/pool.rs L518-528, VUID-vkCreateCommandPool-queueFamilyIndex-01937) and swapchain present checks consult the same list (vulkano/src/swapchain/mod.rs L629). Net: for a spare index >= 1 queue that Godot never submits to, `DefaultQueueMutex` is correct and vulkano can own the queue outright once the family is created with more than one queue — which stock Godot does not do (godot-renderer-integration.md finding 8).

3. **Allocation-level memory import is fully supported — this closes the gap godot-renderer-integration.md finding 8 flagged unverified.** `DeviceMemory::import(device, allocate_info, import_info)` / `try_import` (vulkano@70e3169 vulkano/src/memory/device_memory.rs L127-157) attach `MemoryImportInfo` to the allocation: `Fd { handle_type, fd }` (L1426-1429, `OpaqueFd`/`DmaBuf`) and `Win32 { handle_type, handle: vk::HANDLE }` (L1461-1464, `OpaqueWin32`/`OpaqueWin32Kmt`/`D3D11Texture`/`D3D11TextureKmt` — the D3D11 variants from upstream PR [#2678](https://github.com/vulkano-rs/vulkano/commit/996d37b9), 2025-06-30). Validation requires `khr_external_memory_fd` for FD imports (L1471-1479) and `khr_external_memory_win32` for Win32 (L1517-1525), and lowers to `vk::ImportMemoryFdInfoKHR` / `vk::ImportMemoryWin32HandleInfoKHR` as allocation-info pNext chains (L1581-1602) — the exact structs godot-renderer-integration.md finding 7 named as the import mechanism. Dedication and size rules for Vulkan-created handles are enforced in the doc contract, not the validator (L1417-1425, L1448-1460, "Can't validate, must be ensured by user"). Foreign memory can also be adopted wholesale: `DeviceMemory::from_handle(device, handle, allocate_info)` (L264-301).

4. **Memory export is FD-only; the missing Win32 export is the one real vulkano gap, and it is shim-able without a fork.** `DeviceMemory::export_fd(handle_type)`/`try_export_fd` (vulkano@70e3169 vulkano/src/memory/device_memory.rs L922-943) accepts `OpaqueFd`/`DmaBuf`, requires the type in the allocation's `export_handle_types` (L968-975), and calls `vkGetMemoryFdKHR` (L993). No Win32 twin exists: a full-source grep for `get_memory_win32_handle_khr` finds zero call sites, and upstream master still ends at `export_fd` ([device_memory.rs on master](https://raw.githubusercontent.com/vulkano-rs/vulkano/master/vulkano/src/memory/device_memory.rs), HEAD eb3beec4 2026-05-16; commit history for the file shows no export work since the D3D11 import in 2025). Nothing tracks it upstream: a GitHub issue/PR search for external memory in vulkano-rs/vulkano returns zero open items (search verified non-degenerate with a control query). The workaround: the generated loader struct `DeviceFunctions.khr_external_memory_win32: ash::khr::external_memory_win32::DeviceFn` is loaded for every device (vulkano/autogen-out/fns.rs L236, L388 — vulkano calls `get_memory_win32_handle_properties_khr` through it at vulkano/src/device/mod.rs L1612-1613), and ash 0.38.0+1.3.281's `get_memory_win32_handle` wrapper dispatches `fp.get_memory_win32_handle_khr` (ash-0.38.0+1.3.281 src/extensions/khr/external_memory_win32.rs L10-17). So atlas-rt can call `device.fns().khr_external_memory_win32.get_memory_win32_handle_khr(device.handle(), &vk::MemoryGetWin32HandleInfoKHR { memory: memory.handle(), .. })` — unsafe, unvalidated, ~10 lines.

5. **The standard allocator can produce exportable allocations; per-allocation create-info cannot.** `GenericMemoryAllocatorCreateInfo.export_handle_types: &[ExternalMemoryHandleTypes]` (vulkano@70e3169 vulkano/src/memory/allocator/mod.rs L2444-2452) sets exportable handle types per memory type, and the bump/buddy/free-list allocators thread them into every `MemoryAllocateInfo` they issue (L1359-1373, L1494-1510, L1631-1649, L1835-1855); the per-type array must be either empty or one entry per memory type (L1057-1087). `AllocationCreateInfo` (L788-806) has no export field, so export is configured at allocator construction. Design consequence for the cross-device candidate: an exported handle covers the whole `DeviceMemory` block, so an exportable image must come from an allocator dedicated to it — `dedicated_allocation: true` (L2435-2442) — or from a raw `DeviceMemory::try_allocate` with `MemoryAllocateInfo.export_handle_types` (device_memory.rs L1058), which is the cleaner path for one image per transport buffer.

6. **Image creation exposes everything the RD wrap needs, with one constraint for externally-shared images.** `ImageCreateInfo` (vulkano@70e3169 vulkano/src/image/sys.rs L1717-1762) takes `format`, `extent`, `array_layers`, `mip_levels`, `samples`, `tiling`, `usage`, `stencil_usage`, `sharing`, `initial_layout` (defaults Undefined, L1788), plus `external_memory_handle_types` (L1751-1759) which requires API 1.1 or `khr_external_memory` and — the constraint — `initial_layout == ImageLayout::Undefined` (doc L1755-1756, validator L2944-2947), lowering to `vk::ExternalMemoryImageCreateInfo` (L3208). `RawImage::bind_memory`/`try_bind_memory` (L532-578) binds the allocation and validates external-memory coherence both ways: imported memory requires the image's `external_memory_handle_types` to include the imported type (L920-936, VUID-VkBindImageMemoryInfo-memory-02989) and exported memory must be compatible per `PhysicalDevice::image_format_properties` (L900-916, VUID-VkExportMemoryAllocateInfo-handleTypes-00656); binding goes through `vkBindImageMemory2KHR` (L1038). Layout after creation is entirely caller-controlled on `RawImage` — no vulkano-imposed transitions — while the higher-level `Image` tracks layout state internally (image/mod.rs L113-115, L266) and even has an `ImageMemory::External` backing variant (L139-140); mixing that state tracker with Godot's concurrent use of the wrapped image would drift, so the shared image should be built and transitioned at `RawImage` level.

7. **Semaphores and fences: complete import/export for FD and Win32.** `Semaphore` provides `export_fd`/`export_win32_handle`/`import_fd`/`import_win32_handle`/`import_zircon_handle` (vulkano@70e3169 vulkano/src/sync/semaphore.rs L634, L772, L1033, L1143, L1257), gated on `khr_external_semaphore_fd` (L669) and `khr_external_semaphore_win32` (L816, L1182); `Fence` mirrors it with `export_fd`/`export_win32_handle`/`import_fd`/`import_win32_handle` (vulkano/src/sync/fence.rs L547, L676, L802, L890), gated on `khr_external_fence_fd`/`khr_external_fence_win32` (L585, L715, L926). Raw foreign sync objects are adoptable (`Semaphore::from_handle` semaphore.rs L206-228, `Fence::from_handle` fence.rs L182) with `create_info` declaring `export_handle_types` (semaphore.rs L1384-1385, fence.rs L1032). Capability queries live on `PhysicalDevice`: `external_buffer_properties`/`external_fence_properties`/`external_semaphore_properties` (device/physical.rs L1062, L1179, L1297) returning export/import/compat flag sets, and `Device` offers `memory_fd_properties`/`memory_win32_handle_properties` for non-Vulkan-created handles (device/mod.rs L1428-1436, L1535-1542).

## Decision

**Verdict: vulkano-side feasibility confirmed for both Windows transport candidates; one shim needed.**

| Ticket sub-question | vulkano at pin | Gap | Workaround / blocker |
|---|---|---|---|
| (a) Adopt Godot's instance/physical device/device | Y, zero validation performed | None API-side | Caller must mirror Godot's real create-infos (extensions especially); loader must be the system `vulkan-1.dll` |
| (b) Own queue index >= 1 of Godot's family | Y via `Queue::from_handle` + `QueueMutex` | No public retrieval; `Queue::new` private (by design) | Extension calls `vkGetDeviceQueue2` itself; stock Godot creates 1 queue/family so the index does not exist until ticket 02's hook (or upstream) claims it |
| (c) Memory import (Win32/FD/D3D11) | Y, validated paths + raw adopt | None | Requires the hook-enabled extensions on Godot's device (engine side, ticket 02) |
| (c) Memory export | FD only | No `DeviceMemory::export_win32_handle`; absent upstream, untracked | ~10-line raw call through `Device::fns().khr_external_memory_win32.get_memory_win32_handle_khr` |
| (c) Semaphore/fence import+export (FD+Win32) | Y, complete | None vulkano-side | Godot enables no sync extensions (godot-renderer-integration.md finding 7); CPU-fence bridge stays the sync plan until ticket 02 lands them |
| (d) Image for `texture_create_from_extension` | Y, full usage/format/layout control | External-handle images must start `Undefined` (trivially satisfied) | Build at `RawImage` level; explicit layout transitions; format/usage must match what Godot's wrapper and scene usage require |

For ticket 04 (Windows transport decision): the cross-device candidate's vulkano-side cost is now bounded at one raw-export shim plus an export-configured allocator or raw allocation path; everything else it needs from vulkano exists. The same-device candidate's cost is zero vulkano-side, but it still inherits the stock-Godot queue gap. For ticket 07 (cross-renderer sync): if ticket 02's hook enables the external semaphore/fence extensions on Godot's device, vulkano can participate in GPU-side sync with no further work; until then the CPU-fence bridge remains required by Godot's side, not vulkano's.
