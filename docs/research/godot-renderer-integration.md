# Godot integration of atlas-rt (GDExtension / RenderingServer) — feasibility research

## Executive answer

The owner's proposed mechanism, a Rust GDExtension that "uses the RenderingServer to replace the default renderer", does not work and cannot work today: RenderingServer is the public API surface that drives whatever internal renderer the engine compiled in and selected at boot, and there is no extension-visible seam where a renderer gets chosen (findings 1-3). The one proposal asking for exactly this, [godot-proposals #4287](https://github.com/godotengine/godot-proposals/issues/4287), open since 2022-03-26, has the engine lead on record that a pluggable RenderingDevice is "out of the picture", and a near-identical ask, [#10778](https://github.com/godotengine/godot-proposals/issues/10778), was closed as not planned in two minutes in 2024.

What is feasible today, without forking Godot and without giving up vulkano, is the interop-composite path: a GDExtension adopts Godot's Vulkan handles via RenderingDevice.get_driver_resource() (Vulkan since 4.0; enum at servers/rendering/rendering_device_commons.h L944-973), points vulkano at Godot's VkInstance/VkDevice with vulkano's public adoption APIs (Instance::from_handle, Device::from_handle), renders atlas-rt offscreen into a VkImage living on Godot's device, and hands that raw image to RenderingDevice.texture_create_from_extension() (present in every 4.x release since 4.0.4, rendering_device.h L524 in 4.0.4 through L465 in 4.7-stable; PR [#97304](https://github.com/godotengine/godot/pull/97304) documents it as "takes an incoming VkImage, creates a view, and returns it as TextureID"), which flows into the scene via RS.texture_rd_create() and the Texture2DRD class. Zero CPU copies, zero fork, works on stock 4.2+ and cleanly on 4.7.2 (current stable). The two real costs are engineering risk, not API gaps: on stock 4.7 Godot claims exactly one queue (index 0) in every graphics/compute/transfer-capable family (finding 8), so a same-device vulkano integration has no spare queue handles to adopt unless an upstream change claims more, which promotes the cross-device variant (atlas-rt keeps its own device and queues) to the practical Linux path, with cross-renderer synchronization bridged by CPU fences (finding 8), and the API is documented as internal-grade ("intended for low-level usage", Texture2DRD class docs). The hard blocker for the cross-device variant, importing an externally-created VkImage from atlas-rt's own VkDevice, is confirmed absent from the public RD API (no external-memory import anywhere in rendering_device.h 4.5/4.7, the 4.7 Vulkan driver's device-extension list requests only the optional Linux VK_KHR_EXTERNAL_MEMORY_FD (rendering_device_driver_vulkan.cpp L590-592, explicitly unused by the engine) and nothing for Windows or for external semaphore/fence sync), and enabling those extensions is exactly what open proposals [#13969](https://github.com/godotengine/godot-proposals/issues/13969) / [#15210](https://github.com/godotengine/godot-proposals/issues/15210) and open PR [#114940](https://github.com/godotengine/godot/pull/114940) ask for.

The CPU-copy fallback works on every Godot build of the 4.x line with no extensions and no native handles: atlas-rt reads its result back to host memory and the extension pushes it into an ImageTexture (the path NoesisGUI's Godot plugin documents as its fallback, a GPU-to-CPU copy each rendered frame; see finding 10). Order of magnitude at RGBA8: 1440p is ~14.7 MB/frame (~885 MB/s one-way at 60 fps), 4K is ~33.2 MB/frame (~2 GB/s one-way, ~4 GB/s counting both the readback and the upload). Viable at 1440p, painful at 4K60.

A Godot fork is the only way to actually "replace the renderer", because the renderer classes (RendererCompositor, RendererSceneRenderRD, the storages) are plain C++ classes that never enter ClassDB or extension_api.json (finding 3). Godot 4.7 changed one part of the outlook: it ships a public, GDScript-exposed ray-tracing API on RenderingDevice (blas_create/tlas_create/blas_build/tlas_build, hit-SBT management, raytracing_pipeline_create, raytracing_list_trace_rays), explicitly marked experimental (PRs [#99119](https://github.com/godotengine/godot/pull/99119), [#118377](https://github.com/godotengine/godot/pull/118377)). That makes a second no-fork path thinkable for the future, running atlas-rt's RT shaders through Godot's RD instead of vulkano, but the public acceleration-structure geometry is triangles only (no AABB/procedural geometries, finding 5), which breaks the chunk-AABB design the renderer is built on.

## The question and scope

Can atlas-rt's output be rendered inside another engine, primary target Godot 4.x, via a Rust GDExtension that "uses the RenderingServer to replace the default renderer"?

The premise contains one misconception to correct up front: calling RenderingServer from a GDExtension does not get you a seam into renderer selection. RenderingServer is the client-side facade over the internal renderer; the renderer implementation is instantiated by engine boot code before extensions initialize, chosen from a fixed set of compile-time backends via the project setting rendering/renderer/rendering_method (finding 1). Driving RS calls from an extension means driving the built-in renderer, nothing more.

The ticket asks for: RenderingServer semantics; the GDExtension capability boundary; proposal/roadmap state on pluggable renderers and on exposing ray tracing through RenderingDevice; the realistic interop seam (driver_resource, Texture2DRD, external-image import); gdext (godot-rust) coverage; prior art; and a short contrast with Unity/Unreal. Sources are Godot master plus tags 4.0.4, 4.1, 4.2.2, 4.3, 4.4.1, 4.5, 4.6 and 4.7 fetched directly, gdext 0.5.5 docs, proposal/PR metadata via the GitHub API, and the local Vulkan spec checkout for external-memory semantics. Current stable at research time: Godot 4.7.2-stable (2026-08-18, GitHub releases/latest).

## Findings

1. **RenderingServer is the facade, not the renderer; the renderer is instantiated by boot code with no extension hook.** RenderingServer is registered as an abstract class singleton (GDREGISTER_ABSTRACT_CLASS(RenderingServer), servers/register_server_types.cpp L157 on 4.5-stable, L135 on 4.2.2) and its docs describe it as "the API backend for everything visible" ([class RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)). The implementation, RenderingServerDefault, builds the internal renderer in RenderingServerDefault::_init(): RSG::canvas/viewport/scene get memnew'd, then RSG::rasterizer = RendererCompositor::create() (4.5-stable servers/rendering/rendering_server_default.cpp L216-236; same pattern in the 4.2.2 constructor, rendering_server_default.cpp L395-426). RendererCompositor::create() just calls a function pointer _create_func() (servers/rendering/renderer_compositor.cpp L41-45 on 4.5). The actual RS object is created in main.cpp boot: rendering_server = memnew(RenderingServerDefault(...)); rendering_server->init(); (4.2.2 main/main.cpp L2496-2500, under "Initialize Rendering Server"). Extensions initialize at the SERVERS level right after server registration (main.cpp L751-756 on 4.5-stable, both the real setup and test_setup paths), so an extension always finds the built-in renderer already in place, and the C ABI it is restricted to (core/extension/gdextension_interface.h, header note: "This is a C class header... Together with the JSON file, you should be able to generate any binder", 4.5 L33-35) contains no renderer-creation or renderer-registration hook.

2. **Renderer selection is compile-time backend availability plus a project setting; the method enum is closed.** main.cpp defines the project setting with an enum hint built from compiled-in drivers and validates it: rendering_method must be one of forward_plus, mobile, gl_compatibility, else "Unknown renderer name, aborting" (4.2.2 main.cpp L1867-1874); the driver sets are gated by #ifdef VULKAN_ENABLED / GLES3_ENABLED (L1922-1932); the setting lands as GLOBAL_DEF rendering/renderer/rendering_method (L1960). The Forward+/Mobile renderer is RendererCompositorRD (servers/rendering/renderer_rd/), Compatibility is GLES3. On master (4.6-dev+) the tree was reshuffled (servers/rendering/rendering_method.h/.cpp, rendering_server.h moved into servers/rendering/, renderer_rd/ lost its monolithic renderer_rd.h), but the instantiation chain is unchanged (master rendering_server_default.cpp L243-248, still RendererCompositor::create()).

3. **GDExtension cannot provide a rendering backend: renderer internals are not ClassDB classes, hence not in extension_api.json, hence not callable.** Only ClassDB-registered classes appear in extension_api.json, and the rendering domain registers exactly: RenderingServer (abstract), RenderingDevice (abstract), and the RD helper value classes RDTextureFormat, RDTextureView, RDAttachmentFormat, RDFramebufferPass, RDSamplerState, RDVertexAttribute, RDUniform, RDPipeline state classes, RDShaderSource/SPIRV/File (servers/register_server_types.cpp L164 and L222-239 on 4.5-stable; L232-259 on master, which additionally registers RenderData/RenderSceneData/RenderSceneBuffers plus their Extension subclasses). The renderer internals are plain C++ classes, not Object-derived: RenderingDeviceDriver has no Object base (servers/rendering/rendering_device_driver.h), and the RendererSceneRenderRD/RendererCompositorRD family lives as non-Object implementation classes under servers/rendering/renderer_rd/. Non-Object classes have no registration point at all, so renderer-internal names (RendererRD-era types, RenderingDeviceDriver, RendererViewport) cannot appear in extension_api.json; the api.json itself is no longer checked into the engine tree (core/extension listing on 4.5-stable and 4.7-stable contains only extension_api_dump h/cpp, gdextension_interface files and generator scripts; it is generated and shipped with binaries and vendored by godot-cpp). Engine maintainers confirm the intent: Calinou on #4287, "rendering needs too much low-level access to be doable in a fast enough way with GDExtension" (2022-03-26); reduz, "Implementing a custom RenderingDevice IMO is out of the picture, this is waaaaay too hard to make pluggable" ([#4287 comment](https://github.com/godotengine/godot-proposals/issues/4287), 2023-09-19).

4. **Proposals on replacing the renderer: one long-open, one insta-closed, one active successor, all without movement.** [#4287 "Allow creating custom rendering backends using GDExtension"](https://github.com/godotengine/godot-proposals/issues/4287) (opened 2022-03-26, still open, 88 reactions, 19 comments) is exactly the owner's idea; its thread contains the most concrete roadmap statement available: BastiaanOlij lays out three variants (new RenderingDevice backend; custom scene renderer; full RendererCompositor replacement) and says "adding the option to extend a few more base classes so the RendererCompositor implementation can instantiate those, would allow for the full renderer to be replaced" (2023-09-19), with rburing pointing at the physics-engine precedent PR [godot#65427](https://github.com/godotengine/godot/pull/65427) (project-settings dropdown registration) as the model. Last activity in the thread: a user bump in 2024-06, unanswered. [#10778 "Allow replacing RenderingServer"](https://github.com/godotengine/godot-proposals/issues/10778) (custom renderer + ray tracing from gdext) was closed as not_planned on the day it was filed (2024-09-18). The live successor is [#11142 "Replacing Rendering components from GDExtension"](https://github.com/godotengine/godot-proposals/issues/11142) (open, 2024-11-12, 31 reactions, explicitly noted as superseding #4287), which asks to expose and allow overriding RendererLightStorage/MaterialStorage/MeshStorage/TextureStorage/GI/Fog/CanvasRender/SceneRender/SceneCull/SceneOcclusionCull; core response is cautious: QbieShay, "Rendering internals and hooks are a performance and structure critical..." and Calinou, "focusing on specific hooks for upscaling and frame generation makes more sense, as it's much less work than trying to make the entire renderer replaceable with a GDExtension" (2024-11-13). Related open: [#7916 "Implement a Rendering Compositor"](https://github.com/godotengine/godot-proposals/issues/7916) (2023-09-29). No Godot 5 statement found that commits to pluggable renderers; the only official forward-looking renderer material this run found is the GodotCon US 2026 "Godot Rendering Team Update" talk announcement (long-term renderer vision, no published commitments, [godotengine.org](https://godotengine.org/article/godotcon-us-2026-update/)). Marked as inference: no published Godot 5 renderer-replacement plan could be verified.

5. **Godot's public RenderingDevice gained a real ray-tracing API in 4.7, but triangles only, and it is experimental.** Through 4.6-stable, public RD has zero ray-tracing surface (grep over rendering_device.h on 4.5-stable and 4.6-stable: no raytracing or acceleration-structure methods; internal RT use, e.g. occlusion-culling rays, lives in RendererRD over the internal RDD layer). 4.7-stable exposes the full pipeline path: AccelerationStructureGeometry (vertex/index buffers only, rendering_device.h L1360-1370), blas_create/tlas_create (L1372-1373), AccelerationStructureInstance (L1377-1384), blas_build/tlas_build (L1386-1387), hit_sbt_create/set_pipeline/range_alloc/range_free/range_update (L1420-1425), raytracing_pipeline_create with multi-shader raygen/miss and HitGroup{closest_hit, any_hit, intersection} (L1287-1294, multi-shader support from PR [#118044](https://github.com/godotengine/godot/pull/118044)), and command-list dispatch raytracing_list_begin/bind_raytracing_pipeline/bind_uniform_set/set_push_constant/trace_rays/end (L1620-1625). Landed via PR [#99119](https://github.com/godotengine/godot/pull/99119) (merged 2026-01-27, milestone 4.7: "Functions to create acceleration structures and raytracing pipelines in RenderingDevice"), with instance-descriptor semantics aligned to D3D12/Vulkan (PR [#117148](https://github.com/godotengine/godot/pull/117148)). PR [#118377](https://github.com/godotengine/godot/pull/118377) (merged 2026-04-13, milestone 4.7) marks it all experimental and states the API "is not currently used anywhere in the codebase and is only exposed to GDScript", meaning it is ClassDB-bound and therefore reachable from GDExtension. Two consequences for atlas-rt: (a) the public geometry struct has no AABB/procedural geometry support, so the chunk-AABB intersection-shader design cannot map onto public RD as-is; (b) an RD-based port of atlas-rt is conceivable (vulkano-shaders SPIR-V can be loaded by RD), but it is a rewrite of the pipeline/taskgraph layer onto RD lists and depends on an API Godot itself calls experimental.

6. **The interop seam exists and is versioned: get_driver_resource + texture_create_from_extension + Texture2DRD.** RenderingDevice.get_driver_resource(DriverResource, RID, index) is present on every 4.x tag fetched (rendering_device.h: 4.0.4 L1299, 4.1 L1302, 4.2.2 L1331, 4.3 L1404, 4.4.1 L1616, 4.5 L1657, 4.7 L1957, master L1976; pure virtual in the early tags, plain method later). The DriverResource enum (servers/rendering/rendering_device_commons.h L944-973 on 4.7 and master) hands out, driver-agnostically: LOGICAL_DEVICE, PHYSICAL_DEVICE, TOPMOST_OBJECT (the instance), COMMAND_QUEUE, QUEUE_FAMILY, plus per-resource texture/sampler/buffer/pipeline handles; the older VULKAN_* spellings (DRIVER_RESOURCE_VULKAN_DEVICE, _VULKAN_PHYSICAL_DEVICE, _VULKAN_INSTANCE, _VULKAN_QUEUE, _VULKAN_QUEUE_FAMILY_INDEX) survive as deprecated aliases equal to those five. So a GDExtension can obtain Godot's VkInstance/VkPhysicalDevice/VkDevice/VkQueue as raw integers. RenderingDevice.texture_create_from_extension(type, format, samples, usage, image, width, height, depth, layers, mipmaps=1) takes a raw driver image handle and wraps it into an RD texture: present since 4.0.4 (rendering_device.h L524), signature extended with p_mipmaps by PR [#105570](https://github.com/godotengine/godot/pull/105570) (merged 2025-05-08, milestone 4.5, with a ClassDB compatibility bind referencing 105570 in rendering_device.compat.inc L166-199), Metal implementation by PR [#97304](https://github.com/godotengine/godot/pull/97304) (merged 2024-10-04, milestone 4.4; body: the Vulkan driver "takes an incoming VkImage, creates a view, and returns it as TextureID"). Externally backed textures lacking ownership info are a handled, deliberate case: commit 41fdc55b (2024-09-10, "Vulkan: account for externally backed textures (i.e., created via texture_create_from_extension())") and PR [#96832](https://github.com/godotengine/godot/pull/96832) (debug-mode allocation check fails for foreign textures). On the server side, RS.texture_rd_create(RID, TextureLayeredType) wraps an RD texture RID into a server texture (4.2.2 servers/rendering_server.h L163, 4.5 L198, 4.7 servers/rendering/rendering_server.h L155), texture_get_rd_texture goes back the other way (4.7 L156), and 4.7 adds texture_get_native_handle(RID, srgb) handing out the native handle of a server texture (4.7 L157). RS.get_rendering_device() and RS.create_local_rendering_device() exist since 4.0.4 (servers/rendering_server.h L1593-1594; 4.7 L1032-1033), so an extension can even own a private RD. The user-facing bridge class is Texture2DRD ("Texture for 2D that is bound to a texture created on the [RenderingDevice]", doc/classes/Texture2DRD.xml on 4.2.2, 4.3, 4.7 and master; property texture_rd_rid; class note: "intended for low-level usage with [RenderingDevice]"). Practical caveat from the field: get_driver_resource had a D3D12-specific bug returning 0 on 4.5.1, which matters for DX12-hosted plugins, not for our Vulkan path ([godot-cef README](https://github.com/dsh0416/godot-cef)).

7. **The missing piece is external-memory import, and enabling the extensions at all.** Public RD on 4.5/4.7 has no import API: greps of rendering_device.h find zero external-memory or import methods; texture_create_from_extension wraps an image that already exists on Godot's device, it does not import foreign device memory. Corrected on a second pass over 4.7-stable: the 4.6-dev reshuffle consolidated vulkan_context.cpp away (the file no longer exists on the 4.7 tag; the Vulkan context driver is drivers/vulkan/rendering_context_driver_vulkan.cpp), and the engine's device-extension registration (rendering_device_driver_vulkan.cpp, _initialize_device_extensions L562-618) is not a bare zero: it requests VK_KHR_EXTERNAL_MEMORY_FD as an optional extension on Linux with the comment "We don't actually use this extension, but some runtime components on some platforms can and will fill the validation layers with useless info otherwise if not enabled" (L590-592), and nowhere in that list does it request VK_KHR_external_memory_win32 or any external semaphore/fence variant. Design consequence: on Linux, stock Godot's VkDevice is extension-enabled for memory-FD sharing, so extension code can allocate an image plus imported memory in Godot's device via raw Vulkan (VkImportMemoryFdInfoKHR; local spec docs/vulkan/chapters/memory.adoc L1282-1299) and wrap it with texture_create_from_extension; on Windows stock, this variant stays blocked. GPU-side cross-device synchronization is unenabled on every platform (no external semaphore/fence extensions), so a cross-device integration must bridge sync with CPU fences held on atlas-rt's own device, at the cost of a per-frame host wait. On Windows the needed extension is VK_KHR_external_memory_win32, on Linux VK_EXT_external_memory_dma_buf, on macOS VK_EXT_metal_objects; import semantics are allocation-level VkMemoryAllocateInfo pNext structures (VkImportMemoryWin32HandleInfoKHR / VkImportMemoryFdInfoKHR), see the local spec checkout docs/vulkan/chapters/memory.adoc L1282-1299 (memory import operation section). So the import pattern that works today is: the extension itself drives raw Vulkan on Godot's device (device handle from get_driver_resource), creates the VkImage with imported memory, then hands the image to texture_create_from_extension; this is exactly the flow the multi-planar video proposal author describes as working, D3D11 surface to NT handle to VK_KHR_external_memory_win32 import to plane views ([#15116](https://github.com/godotengine/godot-proposals/issues/15116), open 2026-07-03), and it requires the extensions to be enabled at device creation, which stock Godot does not do. That gap is open upstream right now: [#13969 "Allow enabling additional Vulkan extensions for external memory sharing"](https://github.com/godotengine/godot-proposals/issues/13969) (open, 2026-01-07; table of the three platform extensions; notes "The Vulkan device is created at a very early stage, where add-on or extension can't even have chance to modify it"), its implementation PR [#114940](https://github.com/godotengine/godot/pull/114940) (open, milestone 4.x; adds project setting rendering/rendering_device/vulkan/additional_device_extensions plus a query API), and [#15210](https://github.com/godotengine/godot-proposals/issues/15210) (open, 2026-07-17, "Enable VK_KHR_external_memory (+ _win32/_fd)... to allow zero-copy texture sharing with external renderers"; its author independently confirms the consumption side: "Godot already provides the perfect consumption API for this: RenderingDevice.texture_create_from_extension() plus Texture2DRD, and get_driver_resource() exposes the VkDevice/VkPhysicalDevice needed to allocate on Godot's device"). A second, sync-side gap is open too: [#11567 "Add support for explicit semaphores of RenderingDevice"](https://github.com/godotengine/godot-proposals/issues/11567) (open, 2025-01-15) wants semaphore_create_from_extension to cooperate with texture_create_from_extension. Until #114940 or #15210 lands, cross-device sharing into Godot requires a patched engine or the DLL-hooking workaround godot-cef ships (finding 10). CPU-copy fallback cost, arithmetic at RGBA8: 1440p is 2560x1440x4 B = 14.7 MB/frame = ~885 MB/s one-way at 60 fps; 4K is 3840x2160x4 B = 33.2 MB/frame = ~2.0 GB/s one-way, ~4 GB/s of host traffic with both the readback and upload hops, plus pipeline sync on the readback and a GPU copy on the upload; roughly millisecond-scale at 1440p and several milliseconds of latency and jitter risk at 4K60.

8. **vulkano can adopt Godot's handles, which is what makes the same-device path real; queue ownership is the design risk.** vulkano master exposes public unsafe adoption APIs: Instance::from_handle(library, handle, create_info) and from_handle_borrowed (vulkano/src/instance/mod.rs L520-543), and Device::from_handle(physical_device, handle, create_info) and from_handle_borrowed (vulkano/src/device/mod.rs L483-508); PhysicalDevice handles come from the adopted instance's enumeration (instance/mod.rs L703, L841), so the extension can match Godot's VkPhysicalDevice by handle or UUID among the enumerated set (matching-by-handle specifics are unverified inference; enumerate-then-match is the workaround). External memory exists in vulkano's types and queries: ExternalMemoryHandleType/ExternalMemoryHandleTypes, MemoryFdProperties, MemoryWin32HandleProperties, and memory_fd_properties/memory_win32_handle_properties (device/mod.rs L138, L1408-1454); allocation-level import/export of Godot-imported memory was not verified in this run, so treat the cross-device variant as prototype-first. The load-bearing risk is queue ownership, and a second pass over 4.7-stable shows the spare-queue option assumed earlier does not exist there: _add_queue_create_info (rendering_device_driver_vulkan.cpp L1305-1323, complete in the fetched range) requests exactly one queue per family (max_queue_count_per_family = 1, created at index 0) in EVERY family whose queueFlags intersect GRAPHICS|COMPUTE|TRANSFER — that is, every family useful for rendering work. A logical device only exposes the queues it was created with (VUID-vkGetDeviceQueue-queueIndex-00385; local spec docs/vulkan/chapters/devsandqueues.adoc L3557-3564), so vulkano adopting Godot's 4.7 VkDevice has no spare queue indices to claim: every retrievable handle is one Godot also holds, with the graphics-family queue certainly submitted by the engine and the dedicated compute/transfer family queues likely used by RD transfer workers (inference, engine-internal). Sharing any of those handles for vulkano submissions without a coordination mechanism Godot does not offer is a data race on the externally-synchronized VkQueue. Adopting the VkInstance but creating vulkano's own VkDevice on the same VkPhysicalDevice is spec-legal and ordinary (two logical devices per instance), but it is then the cross-device variant: memory and semaphores are device-scoped, so external memory plus CPU-fence bridging applies (finding 7). Net: the same-device path on stock 4.7 requires an upstream change (claim spare queue indices at device creation) or reliance on queue handles Godot happens never to submit on, which is unmeasured, version-dependent engine-internal behavior. Marked as inference: no shipped plugin runs vulkano on Godot's device today as far as this research found; the pattern is supported by the APIs cited above, not by prior art.

9. **gdext (godot-rust) covers the seam but has a Texture2DRD hole and trails 4.7.** godot 0.5.5 (2026-08-09, latest release; master pushed 2026-09-06) binds RenderingServer and RenderingDevice as normal classes, including the seam methods: docs.rs godot 0.5.5 shows RenderingDevice with texture_create_from_extension, get_driver_resource, texture_update, and RenderingServer with get_rendering_device, create_local_rendering_device, texture_rd_create, texture_get_native_handle ([docs.rs/godot/0.5.5, struct.RenderingDevice](https://docs.rs/godot/0.5.5/godot/classes/struct.RenderingDevice.html)). Godot 4.7 support exists as an API level: gdext v0.5.4 added the api-4-7 level (Changelog, PR [#1641](https://github.com/godot-rust/gdext/pull/1641)), and v0.5.5 carries "Godot 4.6 API level" and "new initialization for Godot 4.7" entries; the default docs.rs build does not show the 4.7 raytracing/blas/tlas/hit_sbt methods on RenderingDevice, so accessing 4.7's RT API from Rust requires the api-4-7 feature level, and whether its generated bindings include those methods is unverified here (inference: since the methods are ClassDB-bound per PR #118377 they should be in the 4.7 api.json and thus generated). Concrete gap: Texture2DRD is not bound in godot 0.5.5 (no docs.rs page, no godot-rust docs page, zero issues mentioning it), so the RS.texture_rd_create to Texture2D bridge needs a GDScript one-liner or a small shim in Rust until gdext binds it.

10. **Prior art shows all three delivery mechanisms in production extensions.** (a) Same-device native wrap: [buresu/godot-spout](https://github.com/buresu/godot-spout) (GDExtension, Spout input/output, "Forward+ D3D12 and Vulkan are supported for input/output"; notes "OpenGL3 input is not supported yet because can not get native input texture handle from godot", confirming the seam exists only on RD backends). (b) External-memory interop, currently gated on engine work: [dsh0416/godot-cef](https://github.com/dsh0416/godot-cef) (CEF in Godot; DX12/Metal accelerated via RenderingServer textures with a native copy, needs 4.6 beta 2+ for the D3D12 driver_resource bug; on Windows/Linux Vulkan "we use hooking to inject extensions for GPU-accelerated rendering (x86_64 only). This is a workaround until godot-proposals#13969 is resolved"); [Huntk23/NoesisGodotNet](https://github.com/Huntk23/NoesisGodotNet) (NoesisGUI, targets Godot 4.7.1: "engine-gated Vulkan interop... The Vulkan path remains inactive on stock Godot until the engine exposes the required external-memory capability; see godot-proposals #15210"; fallback "Readback uses a private GL context and uploads an ImageTexture... at the cost of a GPU-to-CPU copy each rendered frame"). (c) CPU upload: NoesisGodotNet's readback path as quoted; the FFmpeg video-decoder GDExtension line (ohin/daniel-sanche/anyway5 godot-videodecoder lineage) exists for 4.x but its per-frame mechanism was not verified from source in this run (flagged). OS-level transport prior art: [rileyhawk1417/pw-gd](https://github.com/rileyhawk1417/pw-gd) (PipeWire streaming in and out of Godot 4.2+, interops with spout2pw), and the ecosystem gap is tracked by proposal [#13143 "Implement Native Spout/Syphon for GPU Texture Sharing"](https://github.com/godotengine/godot-proposals/issues/13143) (open, 2025-09-07). Window-level fallback: embedding atlas-rt's own winit window as a native child window over the Godot window needs zero engine cooperation but has untested input-capture, z-order, DPI and DWM-alpha implications; no prior art was found, marked as unverified inference. For contrast: Unity ships the seam natively, Texture2D.CreateExternalTexture takes a native texture pointer and wraps it ([Unity docs](https://docs.unity3d.com/ScriptReference/Texture2D.CreateExternalTexture.html)), and Unreal exposes scene-view extension and native-RHI seams to C++ plugins; Godot has neither today, which is the entire content of findings 3 and 4.

11. **Godot 4.7 has a compile-in VulkanHooks seam for instance/device creation, but a GDExtension cannot install it.** drivers/vulkan/vulkan_hooks.h declares a virtual interface with create_vulkan_instance(const VkInstanceCreateInfo*, VkInstance*), get_physical_device(VkPhysicalDevice*), create_vulkan_device(const VkDeviceCreateInfo*, VkDevice*), and set_direct_queue_family_and_index(uint32_t, uint32_t). Call sites: RenderingContextDriverVulkan::_create_vulkan_instance delegates wholesale when a hook is installed (rendering_context_driver_vulkan.cpp L880-882), physical-device selection is overridable (L830-832), and the RD driver's device creation goes through the hook (rendering_device_driver_vulkan.cpp L1495-1497); the driver's own comment names the intended installer: "VulkanHooks detected (e.g. OpenXR): Force-disabling Swappy Frame Pacing" (L1877-1881). The singleton is set only from the hook subclass's constructor (vulkan_hooks.cpp L35-39), and the class is not ClassDB-exported, so the only ways in are compile-in code (module, fork, platform patch) or the DLL-injection workaround godot-cef documents. For atlas-rt this is the sanctioned mechanism that would make the cross-device variant first-class on all platforms (a hook can add VK_KHR_external_memory_win32 plus external semaphore/fence at device creation); exposing it as a project setting is exactly what open PR #114940 proposes.

## Decision

**Verdict: partially feasible.** "Replace the default renderer" via RenderingServer calls from a GDExtension is not feasible and is not what RenderingServer is for; every replace-the-renderer route is fork-only today. The realistic Godot target is the interop-composite path: GDExtension + vulkano adopting Godot's Vulkan handles + texture_create_from_extension + Texture2DRD, which is fully supported by shipped APIs and proven in adjacent projects. CPU copy is the universal fallback. Recommended sequencing (revised after the queue-claim measurement): on Linux, prototype the cross-device variant first — vulkano keeps its own instance/device and all queues (the renderer's compute-queue acceleration-structure design stays untouched), the extension imports the output image into Godot's device via the stock-enabled VK_KHR_EXTERNAL_MEMORY_FD and wraps it — while on Windows that path is gated on PR #114940, #13969/#15210, or a VulkanHooks install. The same-device adoption path needs an upstream queue-count change before it is robust; keep the CPU path as the shipping fallback and watch the open upstream items below before committing to anything fork-shaped.

| Path | Works today | Blockers | Effort | Risk |
|---|---|---|---|---|
| RS calls from GDExtension "replacing the renderer" | N | Not a seam; RS drives the built-in renderer (findings 1-2) | n/a | n/a |
| GDExtension custom renderer backend (RD/Compositor subclass) | N | Renderer internals not exposed, no registration hook; reduz: "out of the picture" (#4287, #10778) | engine-scale | rejected upstream |
| Same-device composite: vulkano adopts Godot device, texture_create_from_extension + Texture2DRD | N on stock 4.7 (no spare queue handles, finding 8); Y after an upstream queue-count change | queue-handle sharing is a data race; upstream change to claim spare indices needed; Texture2DRD unbound in gdext 0.5.5; internal-grade API | medium after upstream | medium |
| Cross-device external-memory import | Partial on stock Godot (Linux FD only; Windows: N) | No RD import API (raw-Vulkan allocation + VkImportMemoryFdInfoKHR inside the extension); Linux FD extension enabled stock (finding 7 correction); GPU-side sync extensions absent everywhere (CPU-fence bridge needed); Windows requires #114940/#13969/#15210 or a VulkanHooks install (finding 11); #11567 still open | medium (Linux prototype); small once upstream lands | medium-high |
| CPU copy (readback to Image/ImageTexture or RD.texture_update) | Y everywhere | ~2-4 GB/s host traffic plus sync at 4K60; fine at 1440p | small | low |
| Fork Godot, implement renderer as module/override | Y | Permanent fork maintenance; renderer internals churn (master reshuffle in 4.6-dev) | very large | high |
| Port atlas-rt onto Godot RD (4.7 public RT API) | Y (4.7+, experimental) | Rewrite onto RD lists; public AS geometry is triangles only, no AABB/procedural; experimental API, gdext coverage unverified | large | medium-high |
| Native child-window overlay (HWND embedding) | Y | Zero engine cooperation; input/z-order/DWM caveats untested, no prior art found | small-medium | unverified |

**What would flip the answer, worth watching:**

- [PR #114940](https://github.com/godotengine/godot/pull/114940) (milestone 4.x) adding rendering/rendering_device/vulkan/additional_device_extensions: merging it turns the cross-device external-memory path into a stock-engine path (no fork, no hooking).
- An upstream change to _add_queue_create_info (drivers/vulkan/rendering_device_driver_vulkan.cpp) claiming spare queue indices per family (Godot keeps index 0): flips the same-device adoption path to stock-engine support, since vulkano could then own indices >= 1; a natural companion to #11567's synchronization work.
- Proposals [#13969](https://github.com/godotengine/godot-proposals/issues/13969) and [#15210](https://github.com/godotengine/godot-proposals/issues/15210): acceptance of either signals first-class support for exactly this use case ("zero-copy texture sharing with external renderers").
- The compile-in VulkanHooks seam (finding 11): already merged, just unreachable from GDExtension; any move to expose it to modules or extensions makes cross-device external memory first-class without a fork.
- [#11142](https://github.com/godotengine/godot-proposals/issues/11142) (supersedes #4287): if the Renderer storage/scene-render exposure progresses, partial or full renderer replacement via GDExtension opens up; the physics precedent ([PR godot#65427](https://github.com/godotengine/godot/pull/65427)) is the registration model to copy.
- [#11567](https://github.com/godotengine/godot-proposals/issues/11567) explicit semaphores: needed for robust cross-renderer synchronization regardless of transport.
- 4.7+ evolution of the public RD RT API (stabilization beyond experimental, and any addition of AABB/procedural geometry to AccelerationStructureGeometry): would make the "run atlas-rt on Godot's RD" path design-compatible with the chunk-AABB renderer.
- gdext binding Texture2DRD and shipping verified api-4-7 RT bindings ([godot-rust/gdext](https://github.com/godot-rust/gdext)).
