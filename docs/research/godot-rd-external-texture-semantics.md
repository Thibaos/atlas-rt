# Godot RenderingDevice external texture semantics for 4.7.2

Facts for the output-contract decision (ADR 0005's ticket 05): what Godot 4.7.2
does to a VkImage wrapped by RenderingDevice.texture_create_from_extension, and
what the Vulkan spec requires when one allocation backs two VkImage objects on
two VkDevices.

Sources and method. Tag verified as 4.7.2-stable (version.py at
raw.githubusercontent.com reports major 4, minor 7, patch 2, status stable).
All Godot claims below cite a local sparse checkout of that tag, HEAD
ed1daf0bf001b61586d9930840f2f1394092c079, read in full, so every line number is
complete-file and no web_fetch 100k-byte truncation scopes any claim here. In
4.7 the RD core moved to servers/rendering/ (no renderer_rd/rendering_device.cpp
on this tag). Commit 41fdc55b and PR 96832 were fetched through the GitHub API.
Vulkan claims cite the local spec checkout at docs/vulkan/chapters/ (Khronos
asciidoc source). That checkout carries chapter prose and commonvalidity
includes but not the generated includes (api/structs, formats/compatibility.adoc
tables), so claims that would rest on those includes are marked inference.
GitHub blob URLs for cited lines take the form
https://github.com/godotengine/godot/blob/4.7.2-stable/<path>#L<first>.

## Findings

1. **texture_create_from_extension wraps a foreign VkImage in a VkImageView and nothing else; it validates no parameter against the real image.** The RD-level method (servers/rendering/rendering_device.cpp L1854-1894, declared at rendering_device.h L465, ClassDB bound at rendering_device.cpp L9056 as "type, format, samples, usage_flags, image, width, height, depth, layers, mipmaps", mipmaps defaulting to 1) copies the caller's type, format, samples, width, height, depth, layers, mipmaps and usage into an RD Texture with zero checks on any of them; the only failure mode is view creation failing at the driver (L1883-1884). The Vulkan driver (drivers/vulkan/rendering_device_driver_vulkan.cpp L2445-2480) casts p_image to VkImage (L2446) and creates one VkImageView: viewType from the TextureType (L2453), format from the DataFormat (L2454), identity swizzle (L2455-2458), baseMipLevel 0 with levelCount p_mipmaps (L2459-2460), layerCount p_layers (L2461), aspect DEPTH only when the caller declared depth-stencil or depth-resolve usage, else COLOR (rendering_device.cpp L1872-1881, driver L2462). The driver's TextureInfo stores no VkImage field and leaves allocation.handle null; it keeps the view, the format, and the view create-info (L2472-2479, flag at rendering_device_driver_vulkan.h L288). Consequences: the RD usage flags are bookkeeping only, and the real usage requirement comes from Vulkan, since the view carries no VkImageViewUsageCreateInfo; the image must have been created with VK_IMAGE_USAGE_SAMPLED_BIT for shader sampling (a non-sampled view fails at use, not at creation, and validation flags it there), plus VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT when the view format differs from the image's own format (see finding 3). The image must equally have been created with the real extent and mip count the caller passes in, because Godot trusts the parameters for size queries, subresource ranges, and descriptor math without ever looking at the image. The tracker is created eagerly: _texture_make_mutable runs at creation (rendering_device.cpp L1886, L7422-7479) and the tracker's usage starts at RESOURCE_USAGE_NONE (rendering_device_graph.h L196; the has_initial_data branch that would preset SHADER_READ_ONLY, rendering_device.cpp L7482-7485, does not fire here). allowed_shared_formats is hardcoded to R8G8B8A8_UNORM and R8G8B8A8_SRGB (rendering_device.cpp L1869-1870), which only constrains later texture_create_shared_from_slice reinterpretations (list check at L1952-1959), not the primary view format. On free, the driver destroys only the view (rendering_device_driver_vulkan.cpp L2592-2604); with allocation.handle null the foreign image and its memory are left untouched. Commit 41fdc55b (2024-09-10, "Vulkan: account for externally backed textures (i.e., created via texture_create_from_extension()), as such textures lack ownership information. More info: #96832") does exactly two things in the driver: it sets created_from_extension = true under DEBUG_ENABLED in the extension bookkeeping, and it relaxes the DEBUG guard in texture_create_shared and texture_create_shared_from_slice from ERR_FAIL_COND_V(!owner_tex_info->allocation.handle) to also pass when created_from_extension is set (diff over rendering_device_driver_vulkan.cpp and its header). PR 96832 ("Vulkan: Remove texture allocation check", closed, not merged; the landed fix is the commit itself, which cites the PR for context) documents the bug it fixed: on DEBUG builds, which the distributed editor ships as default, using an extension texture through texture_create_shared failed with "Condition \"!owner_tex_info->allocation.handle\" is true", breaking external textures as material albedo.

2. **The state tracker transitions the wrapped image, once: UNDEFINED to the first use's layout, and then never again.** Barriers are built by the command graph: _add_texture_barrier_to_command sets prev_layout from the tracker's current usage and next_layout from the new usage through _usage_to_image_layout (rendering_device_graph.cpp L737-755, L126-157), and the Vulkan driver maps RD layouts to VkImageLayout through RD_TO_VK_LAYOUT (rendering_device_driver_vulkan.cpp L326-340) and fills the barrier's image handle from the view create-info, that is, the foreign VkImage itself (L2940-2944). A barrier is emitted whenever the requested usage differs from the tracker's current usage (rendering_device_graph.cpp L564-575), and the command's end assigns the tracker the new usage (L609). Texture sampling records RESOURCE_USAGE_TEXTURE_SAMPLE when a texture enters a sampler-with-texture uniform set (rendering_device.cpp L4476-4481), which maps to TEXTURE_LAYOUT_SHADER_READ_ONLY_OPTIMAL (rendering_device_graph.cpp L136-137) and to VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL (driver L333). So the first sample of an extension texture emits exactly one barrier, VK_IMAGE_LAYOUT_UNDEFINED to VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL, recorded before the draw in the same submit. The tracker's usage then persists: reset_if_outdated clears per-frame indices and stage info but not usage (rendering_device_graph.h L213-227), so a texture sampled every frame gets no further layout transitions; cross-frame ordering rides on previous_frame_stages (rendering_device_graph.cpp L599-603), a Godot-internal mechanism that cannot see atlas-rt's writes. The underlying image cannot stay in VK_IMAGE_LAYOUT_GENERAL through this path: the only usage the tracker maps to GENERAL is storage-image use (TEXTURE_LAYOUT_STORAGE_OPTIMAL at rendering_device_graph.cpp L138-140, driver L329), and there is no public knob to sample in GENERAL; the caller must expect the one UNDEFINED to SHADER_READ_ONLY_OPTIMAL transition. Validation layers see none of the cross-device picture: inference, validation state is per VkDevice, so Godot's device sees a fresh image at initialLayout UNDEFINED and a legal first transition (oldLayout UNDEFINED or the current layout, docs/vulkan/chapters/synchronization.adoc L217-222), and atlas-rt's device tracks its own object; nothing flags the divergence. Two spec-letter cautions for the contract: oldLayout UNDEFINED permits the implementation to discard the transitioned range's contents (synchronization.adoc L221-222), and the external-sharing rules below make a layout transition on one aliasing image affect the set. In practice, UNDEFINED to SHADER_READ_ONLY_OPTIMAL on a sampled color image is a metadata no-op on desktop drivers (inference, not verifiable from sources), which is why the current transport works, but the output contract should not depend on that practice. Godot never issues queue-family ownership barriers for textures (src/dstQueueFamilyIndex are VK_QUEUE_FAMILY_IGNORED, driver L2942-2943), so external ownership transfer is entirely the application's job.

3. **Texture2DRD samples the texture raw; the engine expects the content encoding the view format implies, and the SDR display path passes UNORM values through untouched.** Texture2DRD (scene/resources/texture_rd.h L41-67) holds an RS-level texture created by RS.texture_rd_create(RD RID) (texture_rd.cpp L108-111; ClassDB binding at servers/rendering/rendering_server.cpp L2298, abstract declaration at servers/rendering/rendering_server.h L155) and its get_rid hands that texture to any normal draw; _set_texture_rd_rid accepts only TEXTURE_TYPE_2D, depth <= 1, array_layers <= 1 (texture_rd.cpp L98-100). On the GPU the engine applies no color conversion for extension textures: the view uses the caller's format with identity swizzle (driver L2454-2458), and sampling a UNORM view format returns the stored bytes normalized; sampling an _SRGB view format makes the hardware auto-decode to linear. The engine's SDR display path writes into a UNORM swapchain: _determine_swap_chain_format prefers VK_FORMAT_B8G8R8A8_UNORM and VK_FORMAT_R8G8B8A8_UNORM with VK_COLOR_SPACE_SRGB_NONLINEAR_KHR, and only HDR output picks RGBA16F with linear color spaces (driver L3558-3582). So an sRGB-encoded LDR frame wrapped with an UNORM format is sampled as-is and displayed as-is, with no second encode on the way to the display target. Inference: wrapping with the _SRGB variant would decode at sample and the UNORM swapchain would then display the decoded linear values without re-encoding, which brightens the image by one sRGB application; the decode mechanism is spec fact, the visual consequence is arithmetic. Format constraints: texture_create_from_extension enforces none (finding 1); the constraints are Vulkan's image view rules, view format identical to the image format unless the image has VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT (docs/vulkan/chapters/resources.adoc L6087-6090, VUID-VkImageViewCreateInfo-image-01019), and with MUTABLE_FORMAT the view format must be compatible with the image format, meaning the same compatibility class (L6021-6034, VUID-VkImageViewCreateInfo-image-01761; classes defined as same texel block bit count at docs/vulkan/chapters/formats.adoc L1837-1843, with a 1.4 alpha-format caveat). RGBA8_UNORM, B8G8R8A8_UNORM, R8G8B8A8_SRGB and B8G8R8A8_SRGB are all 32-bit RGBA8 and land in one class, so a shadow image created as B8G8R8A8_UNORM with MUTABLE_FORMAT can be wrapped with any of the four (inference from the rule; the per-class table is a generated include absent from this checkout). For the full-viewport draw the caller declares samples 1, TEXTURE_TYPE_2D, mipmaps 1, layers 1, and usage including TEXTURE_USAGE_SAMPLING_BIT, which the uniform set bind path then checks against the declared flags (rendering_device.cpp L4454-4455).

4. **One allocation, two VkImage objects, two VkDevices: initial layout, ownership, and matching rules.** All citations are the local spec checkout. (a) initialLayout: images normally accept UNDEFINED or PREINITIALIZED (VUID-VkImageCreateInfo-initialLayout-00993, docs/vulkan/chapters/resources.adoc L2431-2434); an image created with VkExternalMemoryImageCreateInfo handleTypes != 0 must use UNDEFINED (VUID-VkImageCreateInfo-pNext-01443, resources.adoc L2436-2441). The exported frame image starts UNDEFINED by rule. (b) Layout tracking and transitions across the set: the section External Resource Sharing (resources.adoc L11141-11216) states the operative rule, "Implementations must: ensure layout transitions performed on one member of a set of identical subresources of identical images that alias the same range of an underlying memory object affect the layout of all the subresources in the set." (L11184-11189), plus "writes to any image subresources in such a set must: not make the contents of memory used by other subresources in the set undefined" (L11191-11193), and that an application can define content through device writes to an identical subresource of another image bound to the same region (L11194-11196). A new image added to the set with initialLayout UNDEFINED does not make content undefined (L11197-11201), and the NOTE (L11203-11214) spells out the consequence: the actual layout of the memory is not undefined, the layout specified in the first transition becomes the true initial layout of the newly bound image, and UNDEFINED at creation is a placeholder. The spec expresses per-image-object layout tracking through this set rule together with the barrier rule that oldLayout must be UNDEFINED or match the current layout of the image subresource range (synchronization.adoc L215-222). (c) Concurrent device access: "Resources should: only be accessed in the Vulkan instance that has exclusive ownership of their underlying memory. Only one Vulkan instance has exclusive ownership of a resource's underlying memory at a given time, regardless of whether the resource was created using VK_SHARING_MODE_EXCLUSIVE or VK_SHARING_MODE_CONCURRENT." (resources.adoc L11145-11149). Ownership transfer requires release in the source instance, completion observed with semaphores or fences, then acquire in the destination (L11150-11162); binding a shared resource does not change ownership, and implicitly taking ownership without a transfer makes the memory's contents undefined (L11175-11182). This is the rule the ADR's CPU-fence bridge works around, since Godot's RD offers no ownership-transfer API (finding 5, and driver L2942-2943 in finding 2). (d) Memory-requirements compatibility: image size requirements are identical for images created with identical VkImageCreateInfo parameters (resources.adoc L9486-9488), and a NOTE says identical parameters alone do not guarantee identical content interpretation, which VK_IMAGE_CREATE_ALIAS_BIT requests explicitly (L9495-9503); binding requires the memory type to appear in the image's memoryTypeBits (L10298-10302), memoryOffset to be a multiple of the image's alignment (L10303-10310), and the image's size requirement to fit in the bound range (L10319-10327). For the cross-device import itself, VUID-VkMemoryAllocateInfo-allocationSize-01742 (opaque FD) and -01743 (OPAQUE_WIN32 / OPAQUE_WIN32_KMT) require allocationSize and memoryTypeIndex to match the payload's original allocation (docs/vulkan/chapters/memory.adoc L1523-1528, L1549-1555), and NT or global-share handles take memoryTypeIndex from vkGetMemoryWin32HandlePropertiesKHR (memory.adoc L1544-1548). (e) Format and extent matching: same-instance consistency requires identical creation parameters, VK_IMAGE_CREATE_ALIAS_BIT on both, and identical binding (resources.adoc L11496-11505); for the cross-device case the spec states directly, "Aliases created by binding the same memory to resources in multiple Vulkan instances or external APIs using external memory handle export and import mechanisms interpret the contents of the memory in consistent ways, and data written to one alias can: be read by the other alias." (L11539-11544). Inference: that guarantee still presupposes both images describe the same texel data, so creating Godot's shadow image with identical parameters (same format, extent, samples, tiling, mip and layer counts) to atlas-rt's frame image is the safe reading; nothing in this checkout licenses differing extents for a cross-instance import. Aliasing itself is defined over the bound ranges with bufferImageGranularity padding for mixed linear and non-linear resources (L11371-11397), and overlapping uses that include writes must be separated by a memory dependency covering the whole overlapped set (L11619-11624).

5. **The public RD surface has no fence; submit and sync exist only for local devices.** RenderingDevice::submit() and RenderingDevice::sync() (servers/rendering/rendering_device.h L1925-1926, implemented at rendering_device.cpp L7884-7901) error out on the main instance with "Only local devices can submit and sync."; they are usable only on a device obtained from RenderingDevice::create_local_device() (rendering_device.h L1936, implementation L9026, ClassDB bind L9210), which an extension reaches through RenderingServer::create_local_rendering_device() (servers/rendering/rendering_server.h L1033). No fence, semaphore, or timeline object crosses the public RenderingDevice API in 4.7.2. Fences exist only below it: RenderingDeviceDriver::fence_create, fence_wait, fence_free (servers/rendering/rendering_device_driver.h L410-412) and semaphore_create (L418), plus RD's internal per-frame command fences (servers/rendering/rendering_device.h L1698, L1813-1815); none is exposed. Adjacent main-device calls give no safe-to-rewrite signal either: RenderingServer::sync() flushes the cross-thread command queue (servers/rendering/rendering_server_default.cpp L435-441) and ClassDB's force_draw binds to RenderingServer::draw (servers/rendering/rendering_server.cpp L3573), both submission flushes rather than fence surfaces. This confirms ADR 0005's premise: the host-side bridge stays a CPU fence on atlas-rt's own device for v1.
