# VulkanHooks module mechanics on Godot 4.7.2: hook API, mutation rights, install order, Windows build

## Executive answer

Yes on all three counts the transport ticket needs. A Godot 4.7.2 engine module can install a VulkanHooks implementation and is ordered early enough by construction: module code runs at `MODULE_INITIALIZATION_LEVEL_SERVERS` during the server-registration phase of `Main::setup2()`, before the display server boots (and with it the Vulkan instance) and before the rendering server initializes the device (finding 5). At device creation the hook does not merely influence `vkCreateDevice`. It *performs* it: `RenderingDeviceDriverVulkan::_initialize_device()` assembles the `VkDeviceCreateInfo` and hands it to `VulkanHooks::create_vulkan_device()`, and only the hook-absent branch calls `vkCreateDevice` ([rendering_device_driver_vulkan.cpp L1486-1501](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/vulkan/rendering_device_driver_vulkan.cpp)). Through that seam a hook can (i) append `VK_KHR_external_memory_win32` + `VK_KHR_external_semaphore_win32` + `VK_KHR_external_fence_win32`. Stock 4.7.2 requests none of them (finding 3). It can also (ii) raise per-family `queueCount` above Godot's hard-coded one queue per family, subject to two Vulkan invariants (`pQueuePriorities` array length, family-count cap) that make "build your own create info inside the hook" the clean implementation (finding 4). Godot's own queue tracking is sized before the hook runs, so bumped queues stay unclaimed by the engine and remain adoptable via `vkGetDeviceQueue` by a second consumer. That is exactly the spare-queue capability the interop doc (finding 8) found missing on stock. The sanctioned installer is OpenXR itself: `modules/openxr` constructs its `OpenXRVulkanExtension` (a `VulkanHooks` subclass) during module `SERVERS`-level initialization (finding 6), and the driver names it ("VulkanHooks detected (e.g. OpenXR)"; rendering_device_driver_vulkan.cpp L1877-1881). Delivery consequence (finding 7): the hook is compile-in code, so it ships as a custom engine binary: `scons platform=windows target=template_release arch=x86_64` from tag `4.7.2-stable` produces `bin/godot.windows.template_release.x86_64.exe`, referenced as a custom export template (or replacing the official template file); the GDExtension wrapper and `extension_api.json` are untouched, because `VulkanHooks` is a plain C++ class with no ClassDB surface.

## Question and scope

Extends docs/research/godot-renderer-integration.md finding 11 (the seam exists; unreachable from GDExtension) with: the hook's exact mutation rights at instance/physical-device/device creation; whether per-family queue counts may be bumped legally; whether a module-constructed hook is guaranteed installed before `RenderingContextDriverVulkan::_create_vulkan_instance` and the RD driver's device creation (and the fallback paths); the OpenXR module as the named installer; the minimal Windows build recipe for a custom 4.7.2 binary with such a module.

Ref discipline: all line numbers were fetched at tag `4.7.2-stable` (commit `ed1daf0b`, "Bump version to 4.7.2-stable", 2026-08-17). Tag `4.7-stable` is 4.7.0 (`5b4e0cb0`, 2026-06-17); vulkan_hooks.h/.cpp are identical across both and the checked rendering_device_driver_vulkan.cpp anchor lines coincide, while rendering_context_driver_vulkan.cpp (1087 vs 1095 lines) and main.cpp has drifted. This doc cites those at 4.7.2. The maintenance *branch* `4.7` (head `f6ab5db2`) is 3 commits past 4.7.2 and its version string is 4.7.3-rc: building it is not building 4.7.2.

## Findings

1. **The seam's surface; the singleton is installed exclusively by constructing a subclass.** `VulkanHooks` is a plain C++ class with a private static singleton ([vulkan_hooks.h L38-53](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/vulkan/vulkan_hooks.h)): pure virtuals `create_vulkan_instance(const VkInstanceCreateInfo*, VkInstance*)` (L45), `get_physical_device(VkPhysicalDevice*)` (L46), `create_vulkan_device(const VkDeviceCreateInfo*, VkDevice*)` (L47), `set_direct_queue_family_and_index` (L48), plus the fragment-density/subsampled queries (L49-51); `get_singleton()` inline (L52); no public setter exists. The base ctor is the only installer ([vulkan_hooks.cpp L35-39](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/vulkan/vulkan_hooks.cpp)): `if (singleton == nullptr) singleton = this;`. First construction wins, a second live hook silently does *not* replace it, and the dtor clears the singleton (L41-45), so the hook object must outlive rendering teardown. Consultation sites on 4.7.2: physical-device pinning (rendering_context_driver_vulkan.cpp L830-839: with a hook, enumeration collapses to the hook's single device), instance creation (L881-882), fragment-density-offset query (rendering_device_driver_vulkan.cpp L891-892), device creation (L1495-1497), and the Swappy force-off (L1877-1881).

2. **Instance level: stock list has no external-memory extensions, none are needed, and the hook may substitute its own.** `RenderingContextDriverVulkan::initialize()` runs volk → version probe → instance extensions → instance → physical devices ([rendering_context_driver_vulkan.cpp L902-924](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/vulkan/rendering_context_driver_vulkan.cpp)). The stock instance-extension list (L427-461) is: surface + platform WSI surface (required), debug report under validation, `VK_KHR_get_physical_device_properties2`, `VK_EXT_swapchain_colorspace`, portability (Apple), debug utils. There are no external-memory/semaphore/fence instance extensions, and none are required on Godot's API target: the external *capabilities* API is core since Vulkan 1.1 (the local spec checkout gates it on `VK_BASE_VERSION_1_1` without the extension; see docs/vulkan/chapters/capabilities.adoc L13-15 and throughout, and docs/vulkan/appendices/boilerplate.adoc L355-359 for the win32 extension list), and Godot sets `application_api_version = VK_API_VERSION_1_2` whenever the loader is 1.1+ (rcdv L698; 1.0 only as an old-loader fallback, L416). `_initialize_instance()` (L687) builds the `VkInstanceCreateInfo` and calls `_create_vulkan_instance`: hook present → the hook creates the instance wholesale from the passed (const) info and may swap in its own extension arrays/layers/apiVersion exactly as at device level (L880-882); hook absent → stock `vkCreateInstance` (L884-897). A hook that returns false aborts boot with `ERR_CANT_CREATE` (L833, L882). There is no mid-flight fallback to stock.

3. **Device level (item i): the hook receives the fully assembled create info and performs `vkCreateDevice` itself, so it may add the win32 external extensions.** `RenderingDeviceDriverVulkan::initialize()` (L1831) orders: `_initialize_device_extensions()` (L1843) → device checks → `_add_queue_create_info` (L1854-1856) → `_initialize_device` (L1858). The stock requested device-extension list ([rendering_device_driver_vulkan.cpp L565-618](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/vulkan/rendering_device_driver_vulkan.cpp)) contains swapchain (required) and ~25 optional extensions; the only external-memory entry is optional `VK_KHR_EXTERNAL_MEMORY_FD` with the comment "We don't actually use this extension..." (L590-592): zero Windows entries, zero external semaphore/fence entries. `_initialize_device()` builds `VkDeviceCreateInfo` from the enabled set (L1486-1493: `pNext` feature chain, `pQueueCreateInfos`, `ppEnabledExtensionNames`, `pEnabledFeatures`) and then branches: hook → `create_vulkan_device(&create_info, &vk_device)` (L1495-1497); no hook → `vkCreateDevice` (L1498-1501). Because the hook itself performs the device creation, it can create from a fully self-owned create info: stock extension names plus `VK_KHR_external_memory_win32`, `VK_KHR_external_semaphore_win32`, `VK_KHR_external_fence_win32` (optionally the three non-win32 `VK_KHR_external_memory/semaphore/fence` for explicitness), while preserving the driver's `pNext` chain and `pEnabledFeatures`, or mutate in place through the const pointer (the pointee queue-info elements are non-const driver-owned objects; the const qualification is only the field type). No instance-side additions are needed at Godot's 1.2 target (finding 2).

4. **Queue counts (item ii): the hook may raise per-family `queueCount`; two Vulkan invariants constrain the in-place form.** Stock: `_add_queue_create_info` (L1305-1330) requests exactly one queue in every family with any of GRAPHICS|COMPUTE|TRANSFER (mask L1309, skip L1313-1316): `max_queue_count_per_family = 1` (L1310), `queueCount = MIN(family count, 1)` (L1321), and `pQueuePriorities` points at a one-element `static const float` array (L1311, L1322). RD's own tracking is sized from the stock count *before* the hook ever runs (`queue_families[i].resize(create_info.queueCount)`, L1326). A hook may raise the counts (it owns the create info and calls `vkCreateDevice`), but in-place bumping must satisfy: `queueCount ≤` the family's `VkQueueFamilyProperties::queueCount` (VUID-VkDeviceQueueCreateInfo-queueCount-00382, docs/vulkan/chapters/devsandqueues.adoc L3348-3352) and `pQueuePriorities` must be an array of `queueCount` floats in [0,1] (docs/vulkan/chapters/devsandqueues.adoc L3337-3339, VUID-...-pQueuePriorities-00383 L3353-3355). The stock priorities storage is a length-1 **const** array, so an in-place bump requires replacing `pQueuePriorities` with hook-owned storage (writing into the stock array would be UB); building the hook's own `VkDeviceQueueCreateInfo` array + `VkDeviceCreateInfo` avoids the const_cast entirely and is the recommended form. Post-hook engine behavior is unaffected by design: RD retrieves queues only up to its pre-hook sizing (vkGetDeviceQueue loops over `queue_families[i].size()`, L1503-1507), keeping index 0 of every family for itself; the extra created queues exist on the logical device and stay retrievable by the extension consumer (VUID-vkGetDeviceQueue-queueIndex-00385: the queue must have been created, now satisfied). This is precisely the upstream "claim spare queue indices" change the interop doc listed as a stock-engine gap.

5. **Ordering (item iii): a module hook installed at `MODULE_INITIALIZATION_LEVEL_SERVERS` is guaranteed present before both instance and device creation; the absent hook falls back to stock; a late hook is silently ignored.** Module levels mirror the GDExtension levels ([modules/register_module_types.h L35-43](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/modules/register_module_types.h)); the build generates `register_module_types.gen.cpp` dispatching `initialize_<name>_module(p_level)` per module under `#ifdef MODULE_<NAME>_ENABLED` ([modules/SCsub L19-28](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/modules/SCsub); [modules/modules_builders.py L15-28, L43-47](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/modules/modules_builders.py)). Boot order: `Main::setup()` ends with `initialize_modules(MODULE_INITIALIZATION_LEVEL_CORE)` + `register_core_extensions()` under the comment "core extensions must be registered after globals setup and **before display**" (main.cpp@4.7.2 L2281-2282); `setup2()` then runs the servers phase. The phase doc comment states setup2 "registers high level servers and singletons, displays the boot splash, then registers higher level types" (main.cpp L1025-1026). The order inside the servers phase is pinned by `Main::test_setup()` (L746-881), whose header says "The order is the same as in `Main::setup()`... This also combines `Main::setup2()` initialization" (L744-745): `register_server_types()` (L797) → `initialize_modules(MODULE_INITIALIZATION_LEVEL_SERVERS)` (L801) → `initialize_extensions(SERVERS)` (L802) → ... → `rendering_server = memnew(...); rendering_server->init();` (L814-815). The real `setup2` body sits beyond the 100 kB fetch cap of main.cpp (visible head ends L2482), but a commit hunk places it: inside `Error Main::setup2(bool p_show_boot_logo)`, the accessibility-server fallback block at L3293-3310 is immediately followed by `display_server = DisplayServer::create(display_driver_idx, rendering_driver, ...)` (~L3313) ([commit 2de7d5478b](https://github.com/godotengine/godot/commit/2de7d5478b04d5648e21b53e47a52e00a581e3e0), post-image line numbers). Display boot lands deep in setup2, after the registration region. Therefore a hook constructed in `initialize_<name>_module(SERVERS)` exists before (α) `DisplayServer::create` → the context driver's `initialize()` → `_create_vulkan_instance` (rcdv L880-900), and before (β) `rendering_server->init()` → `RenderingDeviceDriverVulkan::initialize()` → `_initialize_device` (rddv L1831-1858, L1495-1501). Practical corroboration: OpenXR installs at exactly this point and hook-dependent Quest builds work (finding 6). Failure modes: no hook → stock paths (rcdv L884, rddv L1499, stock physical-device enumeration rcdv L841-851); hook returns false → `ERR_CANT_CREATE` boot failure, no mid-flight fallback (rcdv L833/L882, rddv L1497); hook installed *late* (after instance/device creation) → never consulted, silently; each call site checks `VulkanHooks::get_singleton() != nullptr` only at its moment.

6. **Prior art: OpenXR is the in-tree installer; module skeleton to copy.** `vulkan_hooks.h` landed with the original OpenXR driver import (commit `a78a9fee71` "Implementing OpenXR driver", 2021-12-14, per the commits-for-path API); 4.7's interface growth came from OpenXR foveation work: [PR #116220](https://github.com/godotengine/godot/pull/116220) (merge `7958080d65`, 2026-03-23) added `use_subsampled_images` to the hook interface and its project setting. The installer class is `OpenXRVulkanExtension : public OpenXRGraphicsExtensionWrapper, VulkanHooks` ([modules/openxr/extensions/platform/openxr_vulkan_extension.h L42](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/modules/openxr/extensions/platform/openxr_vulkan_extension.h)) with all hook virtuals `override final` (L52-58), delegating to `XR_KHR_vulkan_enable2` entry points bound in the same header (L87-91): `xrCreateVulkanInstanceKHR` (cpp L100), `xrGetVulkanGraphicsDevice2KHR` (L148), `xrCreateVulkanDeviceKHR` (L169), `set_direct_queue_family_and_index` (L199), `use_subsampled_images` (L230-236). Install chain: module `SERVERS` level ([modules/openxr/register_types.cpp L154](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/modules/openxr/register_types.cpp)) → if OpenXR enabled, `memnew(OpenXRAPI)` (L246) → `openxr_api->initialize(OS::get_singleton()->get_current_rendering_driver_name())` (L249; the driver name is already fixed by setup()) → `OpenXRAPI::initialize` → `graphics_extension = memnew(OpenXRVulkanExtension)` ([openxr_api.cpp L1708-1718](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/modules/openxr/openxr_api.cpp)) → base ctor installs the singleton. Module skeleton to copy: `modules/<name>/{config.py, SCsub, register_types.h, register_types.cpp, hook class .h/.cpp}`. `config.py` only needs `can_build(env, platform)` + `configure(env)` (openxr's, L1-6, shows the per-platform guard pattern); `SCsub` does `env_modules.Clone()` + `env.add_source_files(env.modules_sources, "*.cpp")`; `register_types.cpp` implements `initialize_<name>_module(ModuleInitializationLevel p_level)` with a `if (p_level == MODULE_INITIALIZATION_LEVEL_SERVERS) { ... memnew(<Hook>()); }` block (gate by a project setting as OpenXR gates by `xr/openxr/enabled`). Docs sanction exactly this shape (custom_modules_in_cpp); see finding 7.

7. **Windows build recipe and distribution.** Toolchain (official [Compiling for Windows](https://docs.godotengine.org/en/4.7/engine_details/development/compiling/compiling_for_windows.html), 4.7 docs tree; the older `contributing/development/...` paths 404 in 4.7): Visual Studio 2019+ (2022 recommended) with the MSVC v143 "{arch} build tools (Latest)" component and "Windows 11 SDK (10.0.22621.0) or newer", Python 3.9+, SCons 4.4+ (`python -m pip install scons`); SCons auto-finds the VS install; MSVC builds must run from cmd/PowerShell, not MSYS2/MinGW shells; D3D12 deps are skippable (`d3d12=no`) and irrelevant to a Vulkan hook. Commands (same page + [buildsystem intro](https://docs.godotengine.org/en/4.7/engine_details/development/compiling/introduction_to_the_buildsystem.html)): template → `scons platform=windows target=template_release arch=x86_64` → `bin/godot.windows.template_release.x86_64.exe`; editor → `scons platform=windows` (editor is the default PC target) → `bin/godot.windows.editor.x86_64.exe`; `production=yes` for a leaner release (static CRT, no debug symbols; its LTO side-effect stays disabled for MSVC on Windows); `debug_symbols=yes` if a .pdb is wanted (Windows always writes a separate .pdb); `vsproj=yes` generates a VS solution. Module wiring ([custom modules in C++](https://docs.godotengine.org/en/4.7/engine_details/engine_api/custom_modules_in_cpp.html)): an in-tree module is just a directory under `modules/` (auto-discovered; registration files must sit at the module top level); out-of-tree: `scons custom_modules="../modules,/abs/path"` (comma-separated, internally absolutized; a same-named custom module shadows the built-in); any module can be excluded with `module_<name>_enabled=no` (also via a root `custom.py`). Version pinning: build the tag `4.7.2-stable` (`ed1daf0b`), not the `4.7` branch (3 commits ahead, version string 4.7.3-rc) and not tag `4.7-stable` (= 4.7.0). Distribution, precisely: the hook is compile-in, so every binary that must exercise it is custom. Players receive the exported game as the **custom template binary**: reference `bin/godot.windows.template_release.x86_64.exe` as a *custom export template* in the project's export preset (Advanced Options required; the Windows page notes custom modules/engine code should be configured this way instead of copying), or drop the built binary into `%APPDATA%\Godot\export_templates\4.7.2.stable\` as `windows_release_x86_64.exe` to replace the official template. Official templates cannot run the module (absent from the binary). What stays vanilla: the GDExtension artifacts, because godot-cpp is built against 4.7.2's `extension_api.json`, which the module does not change (`VulkanHooks` has no ClassDB surface, vulkan_hooks.h L38-53; a module may *add* classes but existing bindings remain compatible), and the custom editor binary (`godot.windows.editor.x86_64.exe`) is needed for development for the same reason the template is.
