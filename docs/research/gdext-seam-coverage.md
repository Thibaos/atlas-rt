# gdext (godot-rust) seam coverage: Texture2DRD, api-4-7, frame drive (0.5.5 / master)

## Executive answer

The gdext side of the interop-composite path is fully covered in godot 0.5.5, and the "Texture2DRD hole" recorded in the renderer-integration research (finding 9) is a false positive: the class is bound in every checked release (0.3.5, 0.4.5, 0.5.5 and master) under gdext's converted name **Texture2Drd** (gdext runs Godot identifiers through heck's PascalCase, so `ClassDB`→`ClassDb`, `Texture2DRD`→`Texture2Drd`, `UniformSetCacheRD`→`UniformSetCacheRd`; the searches behind finding 9 used the Godot spelling). All six seam methods are bound with verified signatures: `RenderingDevice.texture_create_from_extension / get_driver_resource / texture_update` and `RenderingServer.get_rendering_device / texture_rd_create / texture_get_native_handle` ([docs.rs/godot/0.5.5, struct.RenderingDevice](https://docs.rs/godot/0.5.5/godot/classes/struct.RenderingDevice.html), [struct.RenderingServer](https://docs.rs/godot/0.5.5/godot/classes/struct.RenderingServer.html)). No shim is needed: `Texture2Drd::new_gd()` + `set_texture_rd_rid(Rid)` is the whole bridge, and the setter itself marshals to the render thread ([docs.rs/godot/0.5.5, struct.Texture2Drd](https://docs.rs/godot/0.5.5/godot/classes/struct.Texture2Drd.html)). The `api-4-7` feature (added v0.5.4) does not change 0.5.5's default: the default API level of 0.5.5 stays 4.6 (PR [godot-rust/gdext#1641](https://github.com/godot-rust/gdext/pull/1641): "Default version stays 4.6 for now, to avoid breaking changes during godot-rust patch releases. In v0.6.0 we can bump the default."), the six seam surfaces are identical at 4.6 and 4.7, and the feature gates only 4.7-only APIs (the public RD raytracing surface, absent from the default build). Frame drive on stock Windows Godot 4.7 is main-thread-only through every gdext-visible surface: `rendering/driver/threads/thread_model` defaults to `Safe` (=1, rendering on the main thread; `Separate` is an experimental opt-in), `RenderingServer.draw()` is main-thread-asserted, `frame_pre_draw` fires on the calling thread, and `frame_post_draw` fires inside `_draw`, inline on main in the default config, deferred to a main-thread MessageQueue flush in Separate mode ([rendering_server_default.cpp L443-453, L129-134, L229](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/rendering_server_default.cpp)). `godot::task::spawn` is a main-thread runtime, and Godot API calls from other threads are unsupported by default (panicking accessor; only the print family is whitelisted thread-safe since v0.5.4). Consequence: vulkano work can only be submitted outside Godot's frame submission from extension-owned threads against atlas-rt's own device (the cross-device variant); the per-frame surfaces exist for boundary detection and main-thread marshaling, and same-device queue sharing stays out of the design (stock 4.7 exposes no spare queue handles, parent finding 8).

## The question and scope

Ticket 03 asks what godot-rust exposes for the integration seam on 0.5.5 and on master: the six RenderingDevice/RenderingServer methods and their signatures; whether Texture2DRD is bound anywhere and, if not, the cheapest shim; what the `api-4-7` feature level changes for 0.5.5 builds; and which per-frame surface lets a GDExtension submit vulkano work outside Godot's frame submission on Windows Godot 4.7, with the threading guarantees of each. Verified against: docs.rs godot 0.5.5/0.4.5/0.3.5 and the gdext master docs site; the gdext `v0.5.5` tree (Cargo manifests, codegen, special cases, Changelog, PR diffs); godot4-prebuilt `release-v0.5` (the vendored api-JSON source, [workspace Cargo.toml L31](https://github.com/godot-rust/gdext/blob/v0.5.5/Cargo.toml)); Godot raw files at 4.6-stable, 4.7-stable and master; Godot stable class docs. Method notes: docs.rs pages truncate at 100k bytes and list methods in ClassDB bind order (not alphabetical), so presence checks used the page sidebar ("Sections" list); the 11 MB prebuilt api JSON is unreachable (fetch truncation; sandbox TLS blocks curl/pwsh downloads), so Godot-side api.json presence is established by the dump chain (registration macro → `exposed` flag → dump filter) plus gdext's own docs build; Sourcegraph filled tail regions, cross-checked against raw fetches where both existed (identical line numbers).

## Findings

1. **All six seam methods are bound in godot 0.5.5 (default build, API level 4.6) with the following signatures.** RenderingDevice is abstract and final in gdext (page: "Not instantiable / Final class"), so the handle comes from `RenderingServer::get_rendering_device()`:
   - `texture_create_from_extension(&mut self, type_: TextureType, format: DataFormat, samples: TextureSamples, usage_flags: TextureUsageBits, image: u64, width: u64, height: u64, depth: u64, layers: u64) -> Rid`, with `mipmaps` (default 1) behind `texture_create_from_extension_ex`; page doc: "Returns an RID for an existing image (VkImage) with the given type, format, samples, usage_flags, width, height, depth, layers, and mipmaps. This can be used to allow Godot to render onto foreign images." Godot side: [rendering_device.h L465](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/rendering_device.h) (`... uint64_t p_layers, uint64_t p_mipmaps = 1`).
   - `get_driver_resource`: bound (RD page sidebar); Godot: rendering_device.h L1957 `uint64_t get_driver_resource(DriverResource p_resource, RID p_rid = RID(), uint64_t p_index = 0)` → Rust `(resource: DriverResource, resource_backing: Rid, resource_index: u64) -> u64` by the int64→u64 mapping evidenced in the two methods above (exact Rust receiver/width flagged in the sources note).
   - `texture_update(&mut self, texture: Rid, layer: u32, data: &PackedArray<u8>) -> Error`; Godot: rendering_device.h L467 (`RID p_texture, uint32_t p_layer, const Vector<uint8_t> &p_data`).
   RenderingServer (singleton):
   - `get_rendering_device`: bound (RS page sidebar); Godot: `RenderingDevice get_rendering_device() const` ([4.6 docs](https://docs.godotengine.org/en/4.6/classes/class_renderingserver.html), stable docs). Rust-side nullability of the return (Option vs Gd) unverified, so it is flagged.
   - `texture_rd_create(&mut self, rd_texture: Rid) -> Rid`, `layer_type` default 0 behind `_ex`; Godot: [rendering_server.h L155](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/rendering_server.h) (`virtual RID texture_rd_create(const RID &p_rd_texture, const RSE::TextureLayeredType p_layer_type = RSE::TEXTURE_LAYERED_2D_ARRAY) = 0`).
   - `texture_get_native_handle(&self, texture: Rid) -> u64`, `srgb` default false behind `_ex`; Godot: rendering_server.h L157 (`virtual uint64_t texture_get_native_handle(RID p_texture, bool p_srgb = false) const = 0`); doc: "Returns the internal graphics handle for this texture object. For use when communicating with third-party APIs mostly with GDExtension. ... maps to a GLuint (OpenGL) or VkImage (Vulkan)."

2. **Texture2DRD is bound everywhere (0.3.5, 0.4.5, 0.5.5 and master) as Texture2Drd; the recorded hole was a casing artifact.** docs.rs pages 200: [0.5.5](https://docs.rs/godot/0.5.5/godot/classes/struct.Texture2Drd.html), [0.4.5](https://docs.rs/godot/0.4.5/godot/classes/struct.Texture2Drd.html), [0.3.5](https://docs.rs/godot/0.3.5/godot/classes/struct.Texture2Drd.html), [master](https://godot-rust.github.io/docs/gdext/master/godot/classes/struct.Texture2Drd.html); the 0.5.5 page shows Construction (`new_gd()`, "This class is reference-counted"), `set_texture_rd_rid(&mut self, texture_rd_rid: Rid)`, `get_texture_rd_rid(&self) -> Rid`, Deref to Texture2D. The conversion is gdext's heck-based `to_pascal_case` ([godot-codegen/src/conv/name_conversions.rs L46-63 @v0.5.5](https://github.com/godot-rust/gdext/blob/v0.5.5/godot-codegen/src/conv/name_conversions.rs)); the 0.5.5 classes index lists "Texture2Drd, Godot class Texture2DRD", "ClassDb, Godot class ClassDB", "UniformSetCacheRd", "TextureLayeredRd" (same family: all four plus FramebufferCacheRd and Texture3Drd return 200). Godot-side the class is registered exposed, so it is in extension_api.json by construction: [register_scene_types.cpp L979-985 @4.7-stable](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/scene/register_scene_types.cpp) (L980 `GDREGISTER_CLASS(Texture2DRD)`, L981 `GDREGISTER_ABSTRACT_CLASS(TextureLayeredRD)`, L982-985 the layered variants), [4.6-stable L1080-1086](https://raw.githubusercontent.com/godotengine/godot/4.6-stable/scene/register_scene_types.cpp) (L1081), master L999-1004; the exposure chain is [class_db.h L568-571](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/core/object/class_db.h) (`GDREGISTER_CLASS` → `register_class`) + class_db.h L252 (`t->exposed = true`) + [extension_api_dump.cpp L919-922](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/core/extension/extension_api_dump.cpp) (dump keeps only `ClassDB::is_class_exposed` classes). Issue searches for "Texture2DRD" in godot-rust/gdext and godotengine/godot-cpp return 0 results: there was never a gap to report.

3. **Construction semantics: texture_rd_rid takes the RD texture RID; the class validates, wraps server-side, and owns the server texture.** [texture_rd.cpp @4.7-stable](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/scene/resources/texture_rd.cpp) (full): `set_texture_rd_rid` marshals to the render thread (`call_on_render_thread`, L78-91); `_set_texture_rd_rid` (L93-115) rejects invalid RD textures (`texture_is_valid`, L95) and non-2D shapes (L97-100), then wraps via `RS.texture_rd_create(p_texture_rd_rid)` (L108/110); `get_rid()` returns the SERVER texture RID (L56-63, placeholder fallback); the destructor frees the server texture via `RS.free_rid`. Server side, `RS.texture_rd_create` is macro-generated ([rendering_server_default.h L158-167](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/rendering_server_default.h), instantiated at L266): `texture_allocate()` then `texture_rd_initialize(ret, rd_rid, layer_type)`, inline when called on the server thread or `can_create_resources_async()`, else pushed to the command queue; `texture_rd_initialize` ([texture_storage.cpp L2137-2218](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/renderer_rd/storage_rd/texture_storage.cpp)) validates the RD RID (L2138), rejects shared RD textures (L2141) and requires `TEXTURE_USAGE_SAMPLING_BIT` (L2144), and wraps a `texture_create_shared` VIEW (L2201-2202: "We create a shared texture here even if our view matches, so we don't obtain ownership."). Lifetime rule: the server never owns the VkImage, and `RS.free_rid` frees only the server record ("you will want to free the [param rd_texture] using RenderingDevice.free_rid", RenderingServer.xml L4018, SG-indexed tag).

4. **A one-call variant exists, RS.texture_create_from_native_handle, but the engine recommends the two-step.** rendering_server.h L117; ClassDB-bound (rendering_server.cpp L2269, SG-indexed tag); implementation [texture_storage.cpp L1575-1588](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/renderer_rd/storage_rd/texture_storage.cpp) calls `RD.texture_create_from_extension(type, format, TEXTURE_SAMPLES_1, usage_flags, p_native_handle, ..., 1)` then allocate + `texture_rd_initialize` (L1582-1585); bound in gdext 0.5.5 (RS sidebar) with the 4.6-documented signature `(type: TextureType, format: Format, native_handle: int, width: int, height: int, depth: int, layers: int = 1, layered_type: TextureLayeredType = 0) -> RID`; the RS docs note (RenderingServer.xml L3921, SG-indexed tag): "If using only the rendering device renderer, it's recommend to use RenderingDevice.texture_create_from_extension together with RenderingServer.texture_rd_create, rather than this method."

5. **texture_get_native_handle composes with get_driver_resource; the RD-level twin is deprecated in 4.7.** [texture_storage.cpp L2233-2242](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/renderer_rd/storage_rd/texture_storage.cpp): `return RD::get_singleton()->get_driver_resource(RD::DRIVER_RESOURCE_TEXTURE, tex->rd_texture[_srgb])`, the VkImage behind the server texture's shared view. The RS-level method (rendering_server.h L157) is the current API; `RenderingDevice.texture_get_native_handle` is wrapped in `#ifndef DISABLE_DEPRECATED` (rendering_device.h L476-478) with docs "Use get_driver_resource with DRIVER_RESOURCE_TEXTURE instead" (RenderingDevice.xml L1217, SG-indexed tag); it remains bound in 0.5.5 (RD sidebar).

6. **api-4-7 (v0.5.4) does not change 0.5.5's default level or any seam surface; it gates only 4.7-only APIs.** [godot-bindings/src/import.rs @v0.5.5](https://github.com/godot-rust/gdext/blob/v0.5.5/godot-bindings/src/import.rs): the version-sync block emits `version_4_6 as prebuilt` for the no-feature default; `LATEST_API_VERSION = (4, 7, 0)`; PR [godot-rust/gdext#1641](https://github.com/godot-rust/gdext/pull/1641) body: "Default version stays 4.6 for now"; its CI changes label the 4.7 job "Latest stable release (above default API level), thus needs explicit api-4-7" and the 4.6 job "Default API level (no api-* feature); runs against its matching stable binary". Both prebuilts ship ([godot4-prebuilt release-v0.5 src/4.2–4.7](https://github.com/godot-rust/godot4-prebuilt/tree/release-v0.5/src)). The default 0.5.5 RD page has no raytracing surface (sidebar: no blas_*/tlas_*/hit_sbt_*/raytracing_*), while Godot 4.7's stable docs expose `hit_sbt_create` etc., which need `api-4-7` (or `api-custom`). Changelog attributions in the parent doc (finding 9) are misdated: "Godot 4.6 API level" is v0.5.0 (#1484), "Use new initialization for Godot 4.7" is v0.5.3 (#1567), "Follow up Godot 4.7 nullability changes" is v0.5.2 (#1556); v0.5.5's own entries mention no API level. Running on Godot 4.7 requires ≥ 0.5.3 (new initialization); 0.5.5 satisfies it.

7. **Every gdext-visible per-frame surface runs on the main thread in the stock Windows 4.7 configuration.**
   - (a) `Node._process`: gdext's `INode` exposes `process`/`physics_process`/`ready` ([docs.rs/godot/0.5.5, trait.INode](https://docs.rs/godot/0.5.5/godot/classes/trait.INode.html)); Godot-side `_process` is a Node GDVIRTUAL invoked from NOTIFICATION_PROCESS (node.h L433-434, node.cpp L99-101), and scene-tree processing is main-thread ("Interacting with the active scene tree is not thread-safe", [thread_safe_apis.html](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)).
   - (b) RenderingServer signals: `frame_pre_draw`/`frame_post_draw` are RS ClassDB signals (stable docs: "Emitted at the beginning of the frame, before the RenderingServer updates all the Viewports" / "Emitted at the end of the frame, after the RenderingServer has finished updating all the Viewports"); gdext generates `SignalsOfRenderingServer` with `frame_post_draw`/`frame_pre_draw` provider methods ([docs.rs/godot/0.5.5, struct.SignalsOfRenderingServer](https://docs.rs/godot/0.5.5/godot/classes/rendering_server/struct.SignalsOfRenderingServer.html); per-signal `Sig<Name>` types from [signals.rs L134-141 @v0.5.5](https://github.com/godot-rust/gdext/blob/v0.5.5/godot-codegen/src/generator/signals.rs)). Emission ([rendering_server_default.cpp @4.7-stable](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/servers/rendering/rendering_server_default.cpp), complete, 476 lines): `draw()` is main-thread-asserted (L444: "Manually triggering the draw function from the RenderingServer can only be done on the main thread. Call this function from the main thread or use call_deferred()."), emits `frame_pre_draw` on the calling thread (L446), then runs `_draw` inline (L451) or pushes it to the WorkerThreadPool render-pump thread when `create_thread` (L448-449; pump set up in init() L276-288); `_draw` dispatches post-draw steps inline or deferred-to-main (L130-134: `if (create_thread) { ...call_deferred(); } else { _run_post_draw_steps(); }`), and `frame_post_draw` is the last line of `_run_post_draw_steps` (L229), after the rasterizer's `end_frame` (L115).
   - (c) Default thread model: `rendering/driver/threads/thread_model` defaults to Safe (=1): [main.cpp L2751 (master, SG commit 1b4643ae7c8)](https://github.com/godotengine/godot/blob/master/main/main.cpp): `separate_thread_render = (int)GLOBAL_DEF("rendering/driver/threads/thread_model", OS::RENDER_THREAD_SAFE) == OS::RENDER_SEPARATE_THREAD;` with [os.h L51-55](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/core/os/os.h) (`RENDER_THREAD_UNSAFE, RENDER_THREAD_SAFE, RENDER_SEPARATE_THREAD`); the 4.7 hint enum is "Unsafe (deprecated),Safe,Separate" ([project_settings.cpp L1774-1778](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/core/config/project_settings.cpp)); the stable ProjectSettings docs show default 1. Separate is experimental ("several known bugs ... Not recommended for use in production", ProjectSettings.xml L2940 master). No Windows-specific variant exists (the registration and the `--render-thread` CLI block carry no platform ifdefs).
   - (d) `godot::task` (0.5.5): "spawn new async tasks by using the engine as the async runtime", main-thread cooperative async ([docs.rs/godot/0.5.5, godot::task](https://docs.rs/godot/0.5.5/godot/task/index.html)); not a sideband worker.
   - (e) Cross-thread Godot API access is unsupported by default: v0.5.4's "Thread-safe FFI scaffolding" (PR [godot-rust/gdext#1632](https://github.com/godot-rust/gdext/pull/1632)) routes utility functions through a panicking main-thread accessor unless whitelisted: `is_utility_function_thread_safe` approves only the print/push family + `str` (PR #1632 diff, special_cases); the Godot `Thread`/`Mutex`/`Semaphore` classes are deleted from the bindings entirely (godot-codegen special_cases.rs, so use Rust std). In Separate mode `frame_post_draw` still fires on the main thread (deferred via MessageQueue flush, L130-131).
   Conclusion: no Godot-side hook can itself host vulkano submission "outside Godot's frame submission". Submission must live on extension-owned threads against atlas-rt's own VkDevice/queues (the cross-device variant), with the hooks used for boundary detection and main-thread marshaling; touching Godot's own VkQueue from extension code stays unsafe (stock 4.7 claims one queue per graphics/compute/transfer-capable family, parent finding 8).

## Consequences for the blocked tickets

- Extension crate architecture: `godot = "0.5.5"` with default features suffices, because the 4.6-level prebuilt contains every seam surface used here and runs against a Godot 4.7 runtime (new-initialization support landed v0.5.3). Add `features = ["api-4-7"]` only when 4.7-only APIs (RD raytracing) are actually used; it changes nothing else on the seam. No GDScript sidecar, no manual class registration, no ClassDB fallback: the bridge is `RD.texture_create_from_extension(...)` → `RS.texture_rd_create(rd_tex)` (or the bound one-call `RS.texture_create_from_native_handle`, engine-discouraged) → `Texture2Drd::new_gd()` + `set_texture_rd_rid`, upcast to `Gd<Texture2D>` for scene/material assignment; the RID-only server path (no Texture2D object) exists for 2D composition via `RS.canvas_item_add_texture_rect(item, rect, texture: Rid, ...)` + `RS.free_rid` (stable RS docs). CPU-copy fallback: `RD.texture_update(Rid, u32, &PackedArray<u8>)`. A Rust-side Texture2D subclass wrapping an RID is also possible in 4.7 (`Resource::_get_rid` GDVIRTUAL moved to resource.h L119 + resource.cpp L618-628; exposed on gdext's `IResource` as overridable `get_rid`), but is unnecessary given Texture2Drd.
- Frame-loop design space: (i) main-thread coordinator: `INode::process` for pre-draw ticks or `RenderingServer::singleton().signals().frame_post_draw().connect(...)` for the post-submission boundary (both main-thread in every 4.7 configuration); (ii) extension-owned worker thread(s) drive vulkano on atlas-rt's own device, free-running or paced by a channel fed from the coordinator, with zero Godot API calls inside; (iii) handoff: worker publishes fence + image handle; coordinator (main thread) wraps the finished image (`texture_create_from_extension` + `texture_rd_create` + `Texture2Drd`), rotating a double buffer handed to the scene at `frame_post_draw`; the extension retains ownership of every RD texture (`RS.free_rid` does not free the underlying image). Same-device queue sharing is excluded (no spare queue handles on stock 4.7, parent finding 8); on Windows the cross-device image handoff additionally needs the external-memory path still gated upstream (parent findings 7/11), with the CPU-copy path as the shipping fallback.
